# Phase 1: Exception & Infrastructure Foundation

## P1 Stories Satisfied
- Foundation for all 6 P1 stories: every later phase's 401 (bad credentials, bad refresh token), 404 (unknown user), and 409 (duplicate email) responses depend on the `ErrorType`/exception work here. Nothing is reachable over HTTP yet.
- Directly required by every P1 story's "against real Postgres" half: `UserRepository` (the domain port `User.register()`/`changeRole()` already depend on) has **no infrastructure implementation at all today** — confirmed by inspection, only `EventRepositoryImpl`/`TicketTypeRepositoryImpl` exist under `infrastructure/src/main/java/com/tienphat/infrastructure/`. This phase builds it, mirroring `EventRepositoryImpl` exactly.
- FR-09's refresh-token persistence requirement (infra-only, no domain port, `tokenHash` never raw) is built here as inert JPA plumbing, ready for Phase 2's `RefreshTokenStoreImpl` to wrap.

## Requirements
`domain` gains a 5th `ErrorType` value (`UNAUTHORIZED`) and 4 new exceptions this feature's use cases need (`UserNotFoundException`, `DuplicateEmailException`, `InvalidCredentialsException`, `InvalidRefreshTokenException`), following the exact pattern of `EventNotFoundException`/`TicketTypeNotAvailableException`. `presentation`'s existing `GlobalExceptionHandler` is extended to map `UNAUTHORIZED → 401` and to translate Spring Security's `AccessDeniedException → 403`. `infrastructure` gains two brand-new, logic-free JPA persistence slices: `user` (a real `UserRepositoryImpl`, filling a gap that has existed since the domain-layer plan) and `auth` (the infra-only `RefreshToken` entity + Spring Data repository, no domain port — per FR-09). Every new Maven dependency this whole feature needs, across `presentation` and `application`, is added now so later phases never touch a `pom.xml` mid-implementation. No use-case or controller logic exists yet — this phase is verified with direct unit tests and one Testcontainers-backed repository test per new persistence slice.

- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/user/UserRepositoryImpl.java` — `@Repository implements UserRepository`: `save`, `findById`, `findByEmail`, `existsByEmail`, each a thin delegate to `UserJpaRepository` + `UserPersistenceMapper`, mirroring `EventRepositoryImpl`'s constructor-injection style exactly (no `findAll`/pagination — the port doesn't declare one). `save` wraps the delegate's `userJpaRepository.saveAndFlush(...)` call (**not** plain `save` — plan-review finding, HIGH, fixed) in a `try { ... } catch (DataIntegrityViolationException e) { throw new DuplicateEmailException(...); }` — the DB-level unique constraint added to `UserJpaEntity.email` above is only useful if a violation of it surfaces to the caller as the same domain exception `RegisterUserUseCase`'s (Phase 2) `existsByEmail` pre-check throws, not as an unmapped `DataIntegrityViolationException` that would otherwise fall through to `GlobalExceptionHandler`'s generic 500 handler. **`saveAndFlush` is load-bearing, not stylistic**: `UserJpaEntity.id` is app-assigned (no `@GeneratedValue`), so with plain `save` inside `RegisterUserUseCase`'s (Phase 2) own `@Transactional` boundary, Hibernate can defer the INSERT — and the unique-constraint check with it — until that outer transaction commits, which happens *after* this `try/catch` has already returned and closed. By then the resulting `DataIntegrityViolationException` propagates uncaught, past this method, to a generic 500 instead of a 409 — silently defeating the fix in exactly the concurrent-registration scenario it exists for. `saveAndFlush` forces the INSERT (and constraint check) to happen synchronously, inside this method's own `try`, where the `catch` can still see it.

## Risks
- HIGH (plan-review finding, fixed 2026-09-22, re-verified 2026-09-22): the first draft relied solely on `RegisterUserUseCase`'s (Phase 2) application-level `existsByEmail` pre-check to reject duplicate emails — a read-then-write with no atomicity guarantee, so two concurrent `POST /auth/register` calls for the same email could both pass the check before either commits, producing two `User` rows with the same email (breaking `findByEmail`'s single-result contract and enabling account confusion at login). Fixed by adding `@Column(unique = true)` to `UserJpaEntity.email` and translating the resulting `DataIntegrityViolationException` into `DuplicateEmailException` in `UserRepositoryImpl.save` (see above). A second review round caught that this translation silently didn't work as written: `UserJpaEntity.id` is app-assigned (no `@GeneratedValue`), so a plain `save(...)` call inside `RegisterUserUseCase`'s own `@Transactional` method can defer the actual INSERT — and its constraint check — past this method's own `try/catch`, letting the exception escape uncaught to a generic 500 instead of 409 in exactly the race this fix targets. Re-fixed by using `saveAndFlush(...)` instead of `save(...)`, forcing the constraint check synchronously inside the `catch`-guarded scope. Phase 1's own `UserRepositoryImplTest` calls `save` directly with no surrounding use-case transaction, so it would not have caught this — the real proof is deferred to a concurrent-registration test recommended for Phase 5 (mirroring `concurrentRefresh_onlyOneWins`), not yet added as of this plan revision.
- HIGH (blocker-class): if `spring-boot-starter-oauth2-resource-server`/`spring-security-oauth2-jose` don't resolve cleanly against the Boot 4.1.1 BOM, Step 2 is where it surfaces — before any later phase's code depends on them. If this happens, it is a plan-level blocker per the spec's own Assumption, not a workaround-in-place situation.
- MEDIUM: `UserRepositoryImpl` filling a previously-nonexistent gap means this phase is doing more than its "exception + infra foundation" title implies at first glance — flagged explicitly in `plan.md`'s Research Summary #6 so it reads as a deliberate scope correction, not scope creep.
- MEDIUM: `RefreshTokenJpaRepository` is tested directly with no domain-port wrapper — the one deliberate exception to this codebase's normal `XxxRepository` (domain port) → `XxxRepositoryImpl` (infra adapter) pattern; the application-owned `RefreshTokenStore` wrapper arrives in Phase 2, not here.
- LOW: adding `UNAUTHORIZED` to `ErrorType` touches a shared enum consumed by an exhaustive `switch` in the existing `GlobalExceptionHandler` — Java requires all cases covered (or a `default`), so a missed update is a compile error, not a silent runtime gap.
