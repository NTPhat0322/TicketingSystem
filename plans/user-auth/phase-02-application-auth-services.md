# Phase 2: Application-Layer Auth & User Services

## P1 Stories Satisfied
- "As a guest, I want to register a CUSTOMER account..." (FR-01) — `RegisterUserUseCase`, business-logic half.
- "As a registered user, I want to log in..." (FR-02) — `LoginUseCase`, credential-check + refresh-token-issuance half (JWT minting is Phase 3/4's job).
- "As a client app, I want to refresh my access token..." (FR-03) — `RefreshUseCase`, validation + rotation half.
- "As a user, I want to log out..." (FR-04) — `LogoutUseCase`, revocation half.
- "As an ADMIN, I want to change another user's role..." (FR-06) — `ChangeUserRoleUseCase`, business-logic half (the `@PreAuthorize` guard is Phase 4's job).
- "As a user, I want my Bearer token to identify me... `GET /users/me`" (FR-11) — `GetUserUseCase`, the lookup half.

## Requirements
All 6 use cases as plain `UseCase<I,O>` classes, split into two packages mirroring the codebase's one-package-per-aggregate convention plus one deliberate addition: `application.user` (register, change role, get-by-id — direct `User` aggregate operations) and `application.auth` (login, refresh, logout — session/token plumbing, backed by the new application-owned `RefreshTokenStore` port introduced here, per `plan.md` Research Summary #4). `RegisterUserUseCase` hard-codes `UserRole.CUSTOMER` — the command type it accepts structurally has no `role` field at all, so there is nothing for a malicious caller to smuggle through even before Phase 4's DTO layer exists. `LoginUseCase`/`RefreshUseCase` both throw a single, message-identical exception regardless of failure cause (unknown email vs. wrong password; unknown vs. expired vs. revoked token), pinning the "no enumeration signal" NFR at the layer that owns the decision. `infrastructure.auth.RefreshTokenStoreImpl` (implementing the new port) is built in this phase too, immediately after the port itself is defined, so nothing is left half-wired.

### Tests to Write First
Write each of these (red) before the class it targets exists, then implement just enough to turn it green:
- `RefreshTokenCryptoTest` (`application`, plain JUnit, no mocks): `hash(raw)` is deterministic (same input → same output) and different inputs → different outputs; `generateRawToken()` called 100 times produces 100 distinct values, and no generated raw value ever equals its own `hash(...)` output (sanity check that hashing actually transforms the input). Drives `RefreshTokenCrypto`, the shared utility every other test below depends on.
- `UserMapperTest` (mirrors `EventMapperTest`'s pattern): `User → UserResult` preserves `id`/`email`/`fullName`/`phone`/`role`/`createdAt`/`updatedAt`; `UserResult` has no field that could carry `passwordHash` (structural — confirmed by the record's declared component list, not a runtime assertion). Drives `UserResult`/`UserMapper`.
- `RegisterUserUseCaseTest` (mocked `UserRepository`, `PasswordEncoder`, `UserMapper`): success calls `passwordEncoder.encode(command.password())` (never persists the raw password — verified via `ArgumentCaptor` on `userRepository.save(...)`, asserting the saved `User`'s `passwordHash` equals the mock's encoded output, not the raw input) and the saved `User.getRole()` is always `CUSTOMER`; throws `DuplicateEmailException` when `userRepository.existsByEmail` is `true`, without ever calling `save`; a blank `fullName` in the command still surfaces as `InvalidUserDataException` (propagated from `User.register()`, not swallowed).
- `ChangeUserRoleUseCaseTest` (mocked `UserRepository`, `UserMapper`): success updates the role and saves; throws `UserNotFoundException` for an unknown id, without calling `save`.
- `GetUserUseCaseTest` (mocked `UserRepository`, `UserMapper`): success returns the mapped result; throws `UserNotFoundException` for an unknown id.
- `LoginUseCaseTest` (mocked `UserRepository`, `PasswordEncoder`, `RefreshTokenStore`): success — with `passwordEncoder.matches(...)` stubbed `true` — returns a `LoginResult` whose `userId`/`role` match the found `User`, and asserts (via `ArgumentCaptor` on `refreshTokenStore.issue(...)`) that the `tokenHash` argument is **not equal to** the `LoginResult.refreshToken()` raw value returned to the caller — the closest a unit test gets to pinning "never persist the raw token" at this layer, complementing Phase 1's infra-level `grep`. Throws `InvalidCredentialsException` when `userRepository.findByEmail` returns empty; throws the *same* exception type with the *same* message when the user is found but `passwordEncoder.matches` returns `false` — asserted as a single parameterized/two-case test comparing both exceptions' `getMessage()` for equality, pinning the no-enumeration NFR. **Timing-safety test (plan-review finding, CRITICAL):** an additional case for the unknown-email path asserts `passwordEncoder.matches(...)` was still invoked exactly once (via `verify`), with `DUMMY_BCRYPT_HASH` as its second argument — proving the use case does not short-circuit before the comparison, which is the actual mechanism the timing-safety fix depends on (a unit test can't measure wall-clock time reliably, but it can pin that the same code path always runs).
- `RefreshUseCaseTest` (mocked `UserRepository`, `RefreshTokenStore`): valid, non-expired, non-revoked token (mocked `findByTokenHash` returns a matching `RefreshTokenRecord`, `revokeIfActive(record.id())` stubbed `true`) → returns a new `LoginResult` whose `refreshToken` differs from the presented raw token, and verifies `refreshTokenStore.revokeIfActive(record.id())` was called exactly once and `refreshTokenStore.issue(...)` was called with a fresh hash; the returned `role` reflects the **current** `User.getRole()` (mocked to differ from what it might have been at original login — covers an ADMIN promotion happening between login and refresh); throws `InvalidRefreshTokenException` for an unknown hash (`findByTokenHash` empty), an already-revoked record (`revokedAt != null`), and an expired record (`expiresAt` in the past) — three separate cases, none of which call `revokeIfActive`/`issue`. **Race-safety test (plan-review finding, HIGH):** an additional case stubs `findByTokenHash` to return a valid, non-expired, non-revoked record but `revokeIfActive(record.id())` to return `false` (simulating a concurrent request that already won the race and revoked the row a moment earlier) — asserts `RefreshUseCase` throws `InvalidRefreshTokenException` and `refreshTokenStore.issue(...)` is never called, proving the losing side of a race never mints a second live token pair from one presented refresh token. A true multi-threaded reproduction (two real concurrent calls) lives in Phase 5's integration suite, not here.
- `LogoutUseCaseTest` (mocked `RefreshTokenStore`): a token that resolves to a record → `revokeIfActive(record.id())` called once, method returns normally (no exception); a token that does not resolve (`findByTokenHash` empty) → `revokeIfActive` never called, method still returns normally — pins FR-04's idempotent-safe requirement ("revoking an already-revoked/unknown token also returns 204... never leaks whether a token existed") at the layer that owns it.

## Files to Create/Modify
- CREATE `application/src/main/java/com/tienphat/application/user/UserResult.java` — `record(UUID id, String email, String fullName, String phone, UserRole role, Instant createdAt, Instant updatedAt)` — no `passwordHash`.
- CREATE `application/src/main/java/com/tienphat/application/user/UserMapper.java` — `@Mapper(componentModel = "spring")`: `UserResult toResult(User user)`.
- CREATE `application/src/main/java/com/tienphat/application/user/RegisterUserCommand.java` — `record(String email, String password, String fullName, String phone)` — no `role` field, by design.
- CREATE `application/src/main/java/com/tienphat/application/user/RegisterUserUseCase.java` — `@Transactional implements UseCase<RegisterUserCommand, UserResult>`. Constructor: `(UserRepository, PasswordEncoder, UserMapper)`. `execute`: throws `DuplicateEmailException` if `userRepository.existsByEmail(cmd.email())`; else `User.register(UUID.randomUUID(), cmd.email(), cmd.phone(), passwordEncoder.encode(cmd.password()), cmd.fullName(), UserRole.CUSTOMER)`, saves, maps.
- CREATE `application/src/main/java/com/tienphat/application/user/ChangeUserRoleCommand.java` — `record(UUID id, UserRole newRole)`.
- CREATE `application/src/main/java/com/tienphat/application/user/ChangeUserRoleUseCase.java` — `@Transactional implements UseCase<ChangeUserRoleCommand, UserResult>`. Constructor: `(UserRepository, UserMapper)`. `execute`: `findById(cmd.id()).orElseThrow(() -> new UserNotFoundException(...))`, `user.changeRole(cmd.newRole())`, saves, maps.
- CREATE `application/src/main/java/com/tienphat/application/user/GetUserUseCase.java` — no `@Transactional` (read-only, mirrors `GetEventUseCase`) `implements UseCase<UUID, UserResult>`. Constructor: `(UserRepository, UserMapper)`.
- CREATE `application/src/main/java/com/tienphat/application/auth/RefreshTokenStore.java` — the application-owned port (see `plan.md` Research Summary #4): `interface RefreshTokenStore { RefreshTokenRecord issue(UUID userId, String tokenHash, Instant expiresAt); Optional<RefreshTokenRecord> findByTokenHash(String tokenHash); boolean revokeIfActive(UUID tokenId); }`. **`revokeIfActive` returns `boolean`, not `void`** (plan-review finding, HIGH, fixed) — `true` only if it revoked a row that was still active (`revoked_at IS NULL`) at the moment of the update; `false` if the row was already revoked (by a racing concurrent call) or didn't exist. This is what lets `RefreshUseCase` detect and reject the race below instead of silently issuing two live "next" tokens from one presented token.
- CREATE `application/src/main/java/com/tienphat/application/auth/RefreshTokenRecord.java` — `record(UUID id, UUID userId, String tokenHash, Instant expiresAt, Instant revokedAt)`.
- CREATE `application/src/main/java/com/tienphat/application/auth/RefreshTokenCrypto.java` — package-visible final utility class, static methods only: `static String generateRawToken()` (`SecureRandom`, ≥32 bytes, URL-safe Base64-encoded, no padding); `static String hash(String raw)` (`MessageDigest.getInstance("SHA-256")`, hex-encoded). No Spring dependency — pure JDK.
- CREATE `application/src/main/java/com/tienphat/application/auth/LoginCommand.java` — `record(String email, String password)`.
- CREATE `application/src/main/java/com/tienphat/application/auth/LoginResult.java` — `record(UUID userId, UserRole role, String refreshToken)` — `refreshToken` is the raw value, returned to the caller exactly once.
- CREATE `application/src/main/java/com/tienphat/application/auth/LoginUseCase.java` — `@Transactional implements UseCase<LoginCommand, LoginResult>`. Constructor: `(UserRepository, PasswordEncoder, RefreshTokenStore)`. `execute`: `Optional<User> found = userRepository.findByEmail(cmd.email())`; **always** call `passwordEncoder.matches(cmd.password(), found.map(User::getPasswordHash).orElse(DUMMY_BCRYPT_HASH))` — a fixed `private static final String DUMMY_BCRYPT_HASH` constant (a precomputed, valid BCrypt hash of an arbitrary fixed string, never matching a real password) — **before** branching, so the unknown-email and wrong-password paths both pay one BCrypt comparison and take comparable time; `if (found.isEmpty() || !passwordMatches) throw new InvalidCredentialsException(SAME_MESSAGE)`; generate raw token, hash it, `refreshTokenStore.issue(user.getId(), hash, Instant.now().plus(7, DAYS))`; return `new LoginResult(user.getId(), user.getRole(), rawToken)`. The unknown-email and wrong-password throw sites use one shared `private static final String` message constant — not two separately-written literals that could drift apart. **Plan-review finding (2026-09-22, CRITICAL, fixed):** the original design short-circuited on `findByEmail(...).orElseThrow(...)` before ever calling `passwordEncoder.matches`, so an unknown email returned in roughly DB-lookup time while a wrong password additionally paid BCrypt's cost factor (tens of ms) — a timing side-channel that leaks email existence despite the identical response *body*, directly undermining the spec's no-enumeration NFR. The always-call-`matches`-first structure above closes it.
- CREATE `application/src/main/java/com/tienphat/application/auth/RefreshUseCase.java` — `@Transactional implements UseCase<String, LoginResult>`. Constructor: `(UserRepository, RefreshTokenStore)`. `execute(rawToken)`: hash it, `findByTokenHash(hash).orElseThrow(InvalidRefreshTokenException::new)`; if `record.revokedAt() != null || record.expiresAt().isBefore(Instant.now())` throw `InvalidRefreshTokenException`; `if (!refreshTokenStore.revokeIfActive(record.id())) throw new InvalidRefreshTokenException(...)` — **the atomic race guard (plan-review finding, HIGH, fixed)**: the preceding `revokedAt`/`expiresAt` check on the already-fetched `record` is a courtesy fast-path only and is *not* what makes this safe under concurrency (that in-memory `record` can be stale the instant two requests read it simultaneously); `revokeIfActive` re-checks and flips `revoked_at` in one atomic, conditional DB statement, so only one of two concurrent callers presenting the same raw token can ever receive `true` — the other gets `false` and must throw here, before generating or issuing anything; generate + issue a new token only after `revokeIfActive` returned `true`; look up the current `User` by `record.userId()` (`orElseThrow(UserNotFoundException::new)`) to get the **current** role, not a stale one; return `new LoginResult(user.getId(), user.getRole(), newRawToken)`.
- CREATE `application/src/main/java/com/tienphat/application/auth/LogoutUseCase.java` — `@Transactional implements UseCase<String, Void>`. Constructor: `(RefreshTokenStore)`. `execute(rawToken)`: hash it, `findByTokenHash(hash).ifPresent(record -> refreshTokenStore.revokeIfActive(record.id()))`; the boolean return of `revokeIfActive` is deliberately ignored here (unlike `RefreshUseCase`) — logout doesn't care whether it won a race against a concurrent refresh/logout on the same token, since either outcome leaves the token revoked, which is all FR-04 requires; returns `null` unconditionally — never throws, by design (FR-04 idempotent-safe).
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/auth/RefreshTokenStoreImpl.java` — `@Repository implements RefreshTokenStore` (from `application.auth`). Constructor: `(RefreshTokenJpaRepository)` (from Phase 1). Hand-written field-by-field mapping between `RefreshTokenJpaEntity` and `RefreshTokenRecord` inline (no MapStruct mapper — 5 flat fields, one direction each way, judged not to warrant a generated mapper class; see Risks). `revokeIfActive(UUID tokenId)` is implemented as a `@Modifying @Query("UPDATE RefreshTokenJpaEntity t SET t.revokedAt = CURRENT_TIMESTAMP WHERE t.id = :tokenId AND t.revokedAt IS NULL")` on `RefreshTokenJpaRepository` (Phase 1), returning the affected-row count as `int`; `revokeIfActive` returns `count == 1`. This single `UPDATE ... WHERE ... AND revoked_at IS NULL` statement is the actual atomicity boundary — Postgres serializes concurrent updates to the same row, so exactly one of two racing calls sees `revoked_at IS NULL` still true and gets `count == 1`; the other's `WHERE` clause matches zero rows.
- CREATE 8 test files mirroring the use cases/mapper above: `RefreshTokenCryptoTest`, `UserMapperTest`, `RegisterUserUseCaseTest`, `ChangeUserRoleUseCaseTest`, `GetUserUseCaseTest`, `LoginUseCaseTest`, `RefreshUseCaseTest`, `LogoutUseCaseTest` (all in `application/src/test/java/com/tienphat/application/{user,auth}/`).
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/auth/RefreshTokenStoreImplTest.java` — Testcontainers-backed (reuses Phase 1's `AbstractPostgresIntegrationTest`/`InfrastructureTestApplication`): `issue` then `findByTokenHash` round-trips every field; `revokeIfActive` on an active record returns `true`, sets `revokedAt`, and a subsequent `findByTokenHash` reflects it; a second `revokeIfActive` call on the now-already-revoked same id returns `false` and leaves `revokedAt` unchanged (proves the `WHERE ... AND revoked_at IS NULL` guard, not just that revocation happens at all). **Concurrency test (plan-review finding, HIGH):** two real concurrent calls to `revokeIfActive(sameTokenId)` — via `ExecutorService`/`CompletableFuture`, each on its own transaction/connection — assert exactly one returns `true` and the other `false`; this is the one place in the whole plan that proves the race is actually closed at the database, not just described in prose (see `plan.md` Risks).

## Risks
- HIGH (plan-review finding, fixed 2026-09-22): the first draft of `RefreshUseCase` used a plain `void revoke(UUID tokenId)` and decided validity purely from the in-memory `RefreshTokenRecord` fetched a moment earlier — two concurrent `/auth/refresh` calls presenting the same raw token could both pass that check before either committed its revoke, both proceeding to issue a new token pair from a single presented token (double-spend). Fixed by making the port method `boolean revokeIfActive(UUID tokenId)`, backed by a single atomic `UPDATE ... WHERE id = ? AND revoked_at IS NULL` at the DB layer (see `RefreshTokenStoreImpl` above); `RefreshUseCase` now treats a `false` return as an authoritative rejection, not just the earlier in-memory check. Proven by `RefreshTokenStoreImplTest`'s concurrency case (Phase 2) and, at the HTTP level, Phase 5's e2e concurrent-refresh test — see `plan.md` Risks.
- MEDIUM: `RefreshTokenStore` is an application-owned port, not a domain one — the single deliberate deviation from every other port in this codebase. See `plan.md` Research Summary #4 for the full justification; restated here because this is the phase that actually introduces it.
- LOW: `RefreshTokenStoreImpl` hand-maps `RefreshTokenJpaEntity ↔ RefreshTokenRecord` without a MapStruct mapper class, unlike `EventPersistenceMapper`/`TicketTypePersistenceMapper` — judged proportionate for a flat 5-field, no-invariant record with no domain object graph to reconstruct (no private constructor, no `@ObjectFactory` need). If this pairing ever grows more fields or logic, revisit and extract a proper mapper.
- LOW: `RefreshUseCase`/`LoginUseCase` share the `LoginResult` shape (see `plan.md` Risks) — acceptable today, would need splitting if refresh-specific response fields are ever needed.
- LOW: `RefreshTokenCrypto.generateRawToken()`'s entropy source and encoding are a single point of failure shared by all 3 callers (`LoginUseCase`/`RefreshUseCase`, implicitly `LogoutUseCase` via the token it's asked to hash) rather than 3 independently-reviewed call sites — mitigated by using `SecureRandom` (never `java.util.Random`) with a generous (≥32-byte) length, called out as non-negotiable in Step 1.
