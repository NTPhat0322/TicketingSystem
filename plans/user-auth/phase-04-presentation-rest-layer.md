# Phase 4: Presentation REST Layer

## P1 Stories Satisfied
- All 6 P1 stories become reachable over HTTP for the first time: register/login/refresh/logout via `AuthController`; role-change + get-me via `UserController`. Every "Accepted when" clause in `spec.md` for the 6 P1 stories gets at least one `@WebMvcTest`-level test here (the "against real Postgres" half is Phase 5's).

## Requirements
`AuthController` (`/api/v1/auth`) with 4 endpoints (`register`, `login`, `refresh`, `logout`); `UserController` (`/api/v1/users`) with `PATCH /{id}/role` (`@PreAuthorize("hasRole('ADMIN')")`) and `GET /me` (identity resolved from the JWT `Authentication` principal's `sub` claim via `@AuthenticationPrincipal Jwt jwt`). `RegisterRequest` has **no `role` field at all** — the strongest possible enforcement of FR-01's "any role field in the request body is ignored" (Jackson silently drops unknown JSON properties by Spring Boot's default `ObjectMapper` config; there is structurally nowhere for a client-supplied `role` to land). `UseCaseConfig` gains 6 new `@Bean` methods wiring Phase 2's use cases to the real `UserRepository`/`RefreshTokenStore`/`PasswordEncoder` beans (from Phase 1's `UserRepositoryImpl`/`RefreshTokenStoreImpl` and Phase 3's `SecurityConfig`). This is the first phase to exercise the real `SecurityConfig` (Phase 3) through an actual `MockMvc` request rather than a bean-existence check — `UserControllerTest` uses `spring-security-test`'s `SecurityMockMvcRequestPostProcessors.jwt()` to simulate Bearer tokens carrying a given `sub`/`role`, rather than hand-crafting raw JWT strings.

### Tests to Write First

- `UserDtoMapperTest`: `UserResult → UserResponse` preserves all 7 fields; `(id, ChangeRoleRequest) → ChangeUserRoleCommand` preserves the path-supplied `id` plus the body's `role`.
- `AuthControllerTest` (`@WebMvcTest(AuthController.class)`, typed `@MockitoBean UseCase<...>` fields + a `@MockitoBean AccessTokenIssuer`):
  - `POST /register` with a fully valid body → 201, `UserResponse` body with `role == CUSTOMER` (the mocked use-case returns a `CUSTOMER` `UserResult` regardless of any extra JSON sent — proves the DTO layer structurally cannot smuggle a role through, since `RegisterRequest` has no `role` component at all: a test case that `POST`s a body containing `"role":"ADMIN"` alongside valid fields still returns `CUSTOMER`, because Jackson silently drops it before it ever reaches the controller). Missing/blank `email` or `password`, or a password shorter than the minimum → 400, use-case never invoked. Mocked use-case throws `DuplicateEmailException` → 409.
  - `POST /login` valid credentials (mocked use-case returns a `LoginResult`, mocked `accessTokenIssuer.issue(...)` returns a fixed string) → 200 + `{accessToken, refreshToken}` matching the mocks. Two separate cases — mocked use-case throws `InvalidCredentialsException` for "unknown email" and, in a second case, for "wrong password" — both → 401 with byte-identical response bodies (asserted by comparing the two `MvcResult` response bodies directly, not just both being 401), pinning the no-enumeration NFR at the HTTP layer.
  - `POST /refresh` valid token (mocked use-case returns a rotated `LoginResult`) → 200 new `{accessToken, refreshToken}`. Mocked use-case throws `InvalidRefreshTokenException` → 401.
  - `POST /logout` any body → 204, no response body, regardless of whether the mocked use-case's `execute` "succeeds" (it always does — `LogoutUseCase` never throws, per Phase 2) — verifies the controller calls `execute` with the request's `refreshToken` and returns 204 unconditionally, proving the idempotent-safe framing lives entirely in the use case, not the controller.
- `UserControllerTest` (`@WebMvcTest(UserController.class)`, typed `@MockitoBean UseCase<...>` fields, using `spring-security-test`'s `jwt()` `RequestPostProcessor` to simulate Bearer tokens):
  - `PATCH /{id}/role` with an ADMIN-role mock JWT + a valid body (mocked use-case returns updated `UserResult`) → 200. A CUSTOMER- or ORGANIZER-role mock JWT on the same request → 403, use-case never invoked. No `Authorization` header at all → 401. An ADMIN-role JWT but an unknown `{id}` (mocked use-case throws `UserNotFoundException`) → 404. An ADMIN-role JWT but a blank/null `role` in the body → 400, use-case never invoked.
  - `GET /me` with a valid mock JWT (any role — a CUSTOMER-role case is enough to prove no role restriction exists) → 200 + `UserResponse` matching the mocked `getUserUseCase` result resolved for that JWT's `sub` claim. No token → 401.

## Success Criteria
- All 6 P1 stories have a passing `@WebMvcTest`-level test for every "Accepted when" clause in `spec.md`.
- `POST /api/v1/auth/register` never returns a non-`CUSTOMER` role, even when the request body includes an extra `"role"` field — pinned by a dedicated test case sending that exact payload.
- Login's and refresh's 401 responses are byte-identical between every distinct failure cause within each endpoint, pinned by direct response-body comparison, not just shared status codes.
- `PATCH /api/v1/users/{id}/role` returns 200 only for an ADMIN-role JWT, 403 for any other authenticated role, 401 for no token, 404 for an unknown id.
- `EventControllerTest`/`TicketTypeControllerTest` (unmodified files) still pass — the FR-10 regression gate.
- `./mvnw -pl presentation -am test` passes.

## Risks
- HIGH: this is the phase where `SecurityConfig`'s rules are first exercised by real request-level tests — if `PATCH /{id}/role`'s `@PreAuthorize` is missing, misspelled (`hasRole` vs `hasAuthority` — `hasRole('ADMIN')` expects the authority to be `ROLE_ADMIN`, which is exactly what `SecurityConfig`'s `JwtAuthenticationConverter` produces, so this must match precisely), or `GET /me` accidentally requires a specific role instead of just authentication, the corresponding `UserControllerTest` case fails immediately and loudly — no silent gap possible given the test coverage above.
- MEDIUM: `GET /api/v1/users/me` resolves identity from the JWT `sub` claim with no fresh existence check at the filter level — restated from `plan.md` Risks, this phase is where it becomes concretely observable (a deleted user's still-valid token authenticates successfully, only failing inside `GetUserUseCase` with a 500-mapped `UserNotFoundException`... actually `NOT_FOUND` → 404, not 500, since `UserNotFoundException` overrides `errorType()`; corrected here from `plan.md`'s more general phrasing — the actual behavior is a 404, still not a 401, which is the only surprising part).
- LOW: `RegisterRequest` returning the fuller `UserResponse` (not a minimal ID-only body) for `POST /register`'s 201 is a slightly stronger contract than FR-01's literal wording ("201 + created user id") — a deliberate, backward-compatible superset, documented here so it isn't mistaken for a missed requirement.
- LOW: `@Size(min = 8)` on `RegisterRequest.password` is a judgment call the spec doesn't explicitly mandate (spec only says "rejects blank/invalid input with 400") — chosen as a minimal, defensible password-hygiene floor consistent with NFR's security framing, not derived from an explicit FR. Flagged here the same way `presentation-layer`'s plan flagged its own `@Future`-omission judgment call.
