# Phase 3: Spring Security Config + JWT Encode/Decode

## P1 Stories Satisfied
- "As an authenticated user, I want my Bearer access token to identify me on protected requests" (FR-05) — the filter chain, `JwtDecoder`, and role-authority mapping that make this possible, end to end at the bean level (the real protected endpoint proving it over HTTP is Phase 4's `/me`).
- Enabling infrastructure for Login/Refresh (FR-02/FR-03): the `JwtEncoder` bean + `AccessTokenIssuer` that Phase 4's `AuthController` will call to actually mint the access token `LoginUseCase`/`RefreshUseCase` (Phase 2) don't produce themselves.
- Enabling infrastructure for Register (FR-01/FR-07): the real `PasswordEncoder` (`BCryptPasswordEncoder`) bean `RegisterUserUseCase` needs at runtime (Phase 2 only needed the *type*, via mocks).

## Requirements
A single hand-wired `presentation.config.SecurityConfig` — per `plan.md` Research Summary #1, Boot 4.1.1's oauth2-resource-server autoconfiguration only handles RSA/issuer-uri, not an HMAC secret, so `JwtEncoder`/`JwtDecoder` are manually defined `@Bean` methods, not auto-configured. `SecurityConfig` also defines the `PasswordEncoder` bean, a `JwtAuthenticationConverter` mapping the JWT's `role` claim to a single `ROLE_<value>` `GrantedAuthority` (and `sub` to the principal name), and the `SecurityFilterChain` itself: stateless sessions, CSRF disabled (stateless JWT API — matches the NFR that access-token validation needs no session store), `permitAll` for the 4 public auth endpoints (register, login, refresh, **and logout** — logout identifies the session from the refresh token in the request body, not from a Bearer access token, so it must stay public; see plan.md Risks for why this was almost missed) + springdoc + **the entire, unmodified `/api/v1/events/**` and `/api/v1/ticket-types/**` prefixes** (FR-10 — enumerated explicitly, not inferred, so this file makes FR-10's guarantee visually auditable), `authenticated()` for everything else. A small `presentation.auth.AccessTokenIssuer` component wraps `JwtEncoder.encode(...)` with this feature's fixed claim set (`sub`, `role`, `iat`, `exp` = now + 15 minutes) so Phase 4's `AuthController` never hand-builds a `JwtClaimsSet` inline. The JWT signing secret is sourced from a new `${JWT_SECRET}` environment variable, mirroring the existing `${DB_URL}`-style convention — never hardcoded. No controllers are protected by anything real yet (Phase 4 adds them); this phase is verified at the bean/claims level, plus an explicit regression check that adding `SecurityConfig` doesn't break the pre-existing Event/TicketType `@WebMvcTest` slices.

### Tests to Write First
Write each of these (red) before the class it targets exists, then implement just enough to turn it green:
- `AccessTokenIssuerTest` (`presentation`, builds a real `NimbusJwtEncoder` directly over a fixed test secret — no Spring context needed): issuing a token for `(userId, ADMIN)` produces a JWT whose decoded claims (verified by round-tripping through a matching `NimbusJwtDecoder` built over the same secret) have `sub == userId.toString()`, `role == "ADMIN"`, and `exp` is approximately 15 minutes after `iat` (asserted with a tolerance, not exact-millisecond equality).
- `SecurityConfigTest` (`presentation`, `@SpringBootTest(classes = PresentationTestApplication.class)`-style context-load slice — confirms wiring, not request-level behavior yet): `PasswordEncoder`, `JwtEncoder`, `JwtDecoder`, and `SecurityFilterChain` beans all exist with the expected types when the context loads; a round-trip — encode a token with the real `JwtEncoder` bean, decode it with the real `JwtDecoder` bean — confirms the claims survive intact through the actual configured beans (not just `AccessTokenIssuerTest`'s standalone pair).
- Regression re-run (not a new test file — an explicit **Step**, matching this phase's Requirements): `EventControllerTest`/`TicketTypeControllerTest` (unmodified) must still pass now that `SecurityConfig` exists and is auto-detected by every `@WebMvcTest` slice in the module (Spring Boot's `WebMvcTypeExcludeFilter` includes `SecurityFilterChain`-producing configuration by design, so this happens automatically, not via an explicit `@Import`).

## Files to Create/Modify
- CREATE `presentation/src/main/java/com/tienphat/presentation/config/SecurityConfig.java` — `@Configuration @EnableWebSecurity @EnableMethodSecurity` (the latter needed for Phase 4's `@PreAuthorize`). Beans:
  - `PasswordEncoder passwordEncoder()` → `new BCryptPasswordEncoder()`.
  - `JwtEncoder jwtEncoder(@Value("${jwt.secret}") String secret)` → `NimbusJwtEncoder` over an `ImmutableSecret<>`/`OctetSequenceKey` built from `secret.getBytes(StandardCharsets.UTF_8)`.
  - `JwtDecoder jwtDecoder(@Value("${jwt.secret}") String secret)` → `NimbusJwtDecoder.withSecretKey(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256")).macAlgorithm(MacAlgorithm.HS256).build()`.
  - `JwtAuthenticationConverter jwtAuthenticationConverter()` → a `JwtGrantedAuthoritiesConverter`-backed converter mapping the `role` claim to a single `SimpleGrantedAuthority("ROLE_" + role)`; principal claim name set to `sub`.
  - `SecurityFilterChain filterChain(HttpSecurity http, JwtAuthenticationConverter converter)` → `.csrf(AbstractHttpConfigurer::disable)`, `.sessionManagement(s -> s.sessionCreationPolicy(STATELESS))`, `.authorizeHttpRequests(auth -> auth.requestMatchers("/api/v1/auth/register", "/api/v1/auth/login", "/api/v1/auth/refresh", "/api/v1/auth/logout", "/v3/api-docs/**", "/swagger-ui/**", "/api/v1/events/**", "/api/v1/ticket-types/**").permitAll().anyRequest().authenticated())`, `.oauth2ResourceServer(oauth2 -> oauth2.jwt(jwt -> jwt.jwtAuthenticationConverter(converter)))`. **`/api/v1/auth/logout` must be in the `permitAll` list** — `LogoutUseCase` (Phase 2) identifies the session purely from the refresh token in the request body, never from a Bearer token, so gating it behind `authenticated()` would make it unreachable once the 15-minute access token has expired, defeating the point of an explicit logout.
- CREATE `presentation/src/main/java/com/tienphat/presentation/auth/AccessTokenIssuer.java` — `@Component`, constructor-injects `JwtEncoder`. `String issue(UUID userId, UserRole role)`: builds `JwtClaimsSet.builder().subject(userId.toString()).claim("role", role.name()).issuedAt(now).expiresAt(now.plus(15, MINUTES)).build()`, returns `jwtEncoder.encode(JwtEncoderParameters.from(claims)).getTokenValue()`.
- MODIFY `bootstrap/src/main/resources/application.yml` — add `jwt.secret: ${JWT_SECRET}`.
- MODIFY `.env.example` — add `JWT_SECRET=` with a placeholder comment (e.g. "generate a real 256-bit secret for any non-local environment").
- MODIFY `docker-compose.yml` — add `JWT_SECRET: ${JWT_SECRET}` to the `app` service's `environment` block.
- MODIFY `presentation/pom.xml` — add `spring-security-test` (test scope) — not yet needed by this phase's own tests, but added here so Phase 4's `UserControllerTest` has it available without another `pom.xml` touch mid-feature.

This file did not exist before this phase (confirmed by inspection) — its absence would otherwise break every existing `@WebMvcTest` the moment `SecurityConfig`'s beans are auto-detected.
- CREATE `presentation/src/test/java/com/tienphat/presentation/auth/AccessTokenIssuerTest.java`.

## Success Criteria
- `AccessTokenIssuerTest` confirms a minted token's `sub`/`role`/`exp`-minus-`iat` are exactly what was requested.
- `SecurityConfigTest` confirms all 4 new beans exist with correct types and a real encode→decode round-trip preserves claims.
- `EventControllerTest`/`TicketTypeControllerTest` (unmodified files) still pass after `SecurityConfig` lands — the FR-10 regression gate this whole phase exists partly to protect.
- `./mvnw -pl presentation -am test` passes.

## Risks
- HIGH: this is the phase where the FR-10 regression risk (see `plan.md` Risks) is first live — `SecurityFilterChain`'s `permitAll` pattern for `/api/v1/events/**`/`/api/v1/ticket-types/**` must cover every HTTP method those controllers use (`GET`, `POST`, `PUT`), not just `GET`, and CSRF must be disabled (a stateless JWT API has no session/cookie to protect against forgery, so disabling it is correct, not a shortcut). Step 5's regression re-run is the direct mitigation.
- HIGH (plan-review finding, fixed 2026-09-22): the first draft of `requestMatchers` omitted `/api/v1/auth/logout`, which would have silently gated logout behind `authenticated()` — unreachable once the access token expires, since `LogoutUseCase` authenticates the caller via the refresh token in the body, not a Bearer token. Fixed by adding it explicitly to the `permitAll` list above.
- MEDIUM: `presentation/src/test/resources/application.yml` did not exist before this phase — every existing `@WebMvcTest` slice in the module (`EventControllerTest`, `TicketTypeControllerTest`, `GlobalExceptionHandlerTest`'s non-Spring test is unaffected) starts depending on it the moment `SecurityConfig`'s `@Value("${jwt.secret}")`-consuming beans are auto-detected. Mitigated by creating it in Step 1, before Step 2's `SecurityConfig` work begins.
- LOW: `SecurityConfigTest`'s bean-existence/round-trip check does not itself prove `authorizeHttpRequests`' path rules are correct at the HTTP level — that proof is deferred to Phase 4 (`UserControllerTest`'s `/me`/`PATCH .../role` cases) and Phase 3's own Step 5 regression check (which proves the *permitAll* half, not the *authenticated* half). Acceptable: no protected endpoint exists yet for a request-level test to target.
