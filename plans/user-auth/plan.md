# Plan: User Authentication & Authorization (Spring Security JWT)
Status: 🟢 Ready for /ck:cook
Date: 2026-09-22
Mode: Hard
Test: --tdd

## Overview
Builds the User module end-to-end — register/login/refresh/logout plus ADMIN-gated role promotion — backed by a hand-wired Spring Security JWT (Nimbus HS256) filter chain, so requests carry a verifiable `userId` + role identity for the first time anywhere in the running system, without touching the existing (and still-`permitAll`) Event/TicketType controllers.

## Phases
- [x] Phase 1: Exception & infrastructure foundation — `ErrorType.UNAUTHORIZED`, 4 new domain exceptions, `GlobalExceptionHandler` extension, real `User` JPA persistence (missing entirely today), infra-only `RefreshToken` JPA persistence, all new module `pom.xml` dependencies
- [x] Phase 2: Application-layer auth & user services — `RegisterUserUseCase`/`ChangeUserRoleUseCase`/`GetUserUseCase` (`application.user`), `LoginUseCase`/`RefreshUseCase`/`LogoutUseCase` (`application.auth`), the application-owned `RefreshTokenStore` port + its infra adapter
- [x] Phase 3: Spring Security config + JWT encode/decode — hand-wired `JwtEncoder`/`JwtDecoder`/`PasswordEncoder`/`SecurityFilterChain` beans, `AccessTokenIssuer`, env-sourced JWT secret
- [x] Phase 4: Presentation REST layer — `AuthController` (register/login/refresh/logout), `UserController` (`PATCH /{id}/role`, `GET /me`), DTOs + MapStruct mappers, `UseCaseConfig` wiring
- [x] Phase 5: End-to-end integration tests + final verification — full-context Testcontainers smoke tests in `bootstrap`, refresh-rotation proof, FR-10 regression re-check, full reactor test run

## Dependency-Graph Reasoning for Phase Ordering
- Phase 1 must land first, for two independent reasons. First, the same reason `presentation-layer`'s Phase 1 came first: every later controller/use-case test asserts a specific status code (401/403/409/404) that depends on `ErrorType.UNAUTHORIZED` and the 4 new domain exceptions existing — without them those assertions don't compile. Second, and specific to this plan: `infrastructure` currently has **no** `User` JPA persistence at all (confirmed by inspection — only `event`/`tickettype` packages exist under `infrastructure/src/main/java/com/tienphat/infrastructure/`), despite the domain's `UserRepository` port having existed since the domain-layer plan. Every later phase's use cases depend on a real `UserRepository` implementation eventually being wired at `bootstrap`'s composition root, so building it as inert, logic-free JPA plumbing now (mirroring `EventJpaEntity`/`EventRepositoryImpl` exactly) removes it as a blocker for Phase 5's end-to-end tests before any auth-specific code depends on it.
- Phase 2 before Phase 3: the application-layer use cases (Phase 2) only need `UserRepository`, `PasswordEncoder` (the type, not a real bean), and the new `RefreshTokenStore` port — all satisfiable with mocks in unit tests, no Spring Security filter chain required yet. Phase 3's `SecurityConfig` is presentation-only wiring; sequencing it after Phase 2 means the `JwtEncoder`/`PasswordEncoder` beans it defines have real, already-tested use cases waiting to consume them in Phase 4, rather than security infrastructure sitting unused.
- Phase 3 before Phase 4: `SecurityConfig` (Phase 3) is a `@Configuration` class producing a `SecurityFilterChain` bean, which Spring Boot's `@WebMvcTest` slice machinery auto-detects for **every** slice test in the module — including the pre-existing `EventControllerTest`/`TicketTypeControllerTest` from the prior plan. Phase 3 is deliberately the single place this module-wide side effect is introduced and immediately regression-checked, before Phase 4 adds the controllers that are supposed to actually be protected by it. Phase 3's own tests stay narrowly scoped to the beans/claims themselves (no real protected endpoint exists yet to test end-to-end request behavior against) — that end-to-end proof happens in Phase 4, once `UserController`'s `/me` endpoint exists as a permanent, real target.
- Phase 4 before Phase 5, mirroring `presentation-layer`'s own reasoning exactly: `presentation`'s `pom.xml` only depends on `application` (hexagonal boundary — no adapter depends on another adapter), so nothing before `bootstrap` can prove `UseCaseConfig`'s beans resolve against the real `UserRepositoryImpl`/`RefreshTokenStoreImpl` (from `infrastructure`) and a real Postgres. Phase 5 is the only phase that proves the full wire-up — including the refresh-token rotation chain, which by definition requires two sequential real HTTP calls against real, persisted state, not something a `@WebMvcTest` mock can meaningfully prove.

## Research Summary
Grounded in two prior passes (brainstorm + spec) that already converged on these decisions — not re-litigated here:
1. **Stateless JWT, HS256 via Spring Security's built-in Nimbus support** (`JwtEncoder`/`JwtDecoder`), hand-wired in a `presentation`-layer `SecurityConfig` — Boot 4.1.1's oauth2-resource-server autoconfiguration only auto-configures RSA/issuer-uri, not HMAC-secret, so both beans are manually defined `@Bean` methods (`NimbusJwtEncoder` over an `OctetSequenceKey`/`ImmutableSecret`; `NimbusJwtDecoder.withSecretKey(...).macAlgorithm(HS256)`).
2. **New dependencies land in `presentation`**: `spring-boot-starter-security`, `spring-boot-starter-oauth2-resource-server`, `spring-security-oauth2-jose` (no explicit `<version>` — Boot 4.1.1 BOM-managed). `application` gains one lightweight dependency, `spring-security-crypto`, purely for the `PasswordEncoder` type its own use cases depend on directly (see decision 3) — not the full framework.
3. **Login/refresh logic is a hand-written `application`-layer service, not a Spring `UserDetailsService`.** `LoginUseCase`/`RefreshUseCase` call `UserRepository.findByEmail` + `PasswordEncoder.matches` directly — deliberately avoiding `org.springframework.security.core.userdetails.UserDetails` ever appearing in `application`/`domain`. The real `BCryptPasswordEncoder` bean is defined in `presentation`'s `SecurityConfig` (Phase 3) and injected into the use-case `@Bean` methods in `UseCaseConfig` (Phase 4), exactly like every existing `EventRepository`/`EventMapper` injection.
4. **`RefreshToken` is infra-only — explicitly no *domain* repository port** (FR-09). This plan's one necessary architectural judgment call, not pre-settled by either research pass: since `application`'s `pom.xml` has no compile-time dependency on `infrastructure`, `LoginUseCase`/`RefreshUseCase`/`LogoutUseCase` still need *some* interface to depend on (Dependency Inversion). Resolution: the port (`RefreshTokenStore`) is defined in `application.auth` instead of `domain.repository` — one layer up from every other port in this codebase (`EventRepository`, `TicketTypeRepository`, `UserRepository`), but still not a domain concept, honoring FR-09's actual intent ("auth plumbing, not a domain aggregate") rather than its most literal reading ("no port anywhere"). `infrastructure.auth.RefreshTokenStoreImpl` implements it, wrapping the infra-only `RefreshTokenJpaRepository`. Flagged prominently in Risks so a future reviewer doesn't mistake this one-off pattern for an inconsistency.
5. **Claims**: `sub` = userId, `role`, `iat`, `exp`. Access token TTL 15 minutes. Refresh token TTL 7 days, single-chain rotation (old token revoked immediately on every successful refresh) — stored as `tokenHash` (SHA-256 of the raw token), the raw value returned to the client exactly once and never persisted or logged.
6. **A genuine gap found during grounding, not previously flagged**: `infrastructure` has **no** `User` JPA persistence at all today — only `EventRepositoryImpl`/`TicketTypeRepositoryImpl` exist, despite the domain's `UserRepository` port existing since the domain-layer plan. This plan's Phase 1 builds `UserJpaEntity`/`UserJpaRepository`/`UserPersistenceMapper`/`UserRepositoryImpl`, mirroring `EventRepositoryImpl` exactly — without it, nothing in this feature could ever run against a real database, and the spec's own success criteria (Testcontainers-backed integration tests) would be unsatisfiable. Also genuinely missing: `UserNotFoundException` (confirmed absent from `domain/exception/` by inspection) — added in Phase 1 per `EventNotFoundException`'s exact pattern.
7. **FR-10 (Event/TicketType untouched) has a real, mechanical regression risk this plan must actively guard against**: once `SecurityConfig` (Phase 3) exists, Spring Boot's `@WebMvcTest` slice machinery auto-detects any `SecurityFilterChain`-producing `@Configuration` class in scope — including for the *pre-existing* `EventControllerTest`/`TicketTypeControllerTest`, which today run with no security configured at all. `SecurityConfig`'s `authorizeHttpRequests` rule must `permitAll` the entire `/api/v1/events/**` and `/api/v1/ticket-types/**` prefixes (all HTTP methods, not just `GET`) and disable CSRF (stateless JWT API), or those two pre-existing, unmodified test files silently start failing. Phase 3 and Phase 4 each include an explicit regression-check step for this; Phase 5's final verification re-confirms it at the full reactor level.
8. **`ErrorType` gains a 5th value, `UNAUTHORIZED`** — the existing enum (`VALIDATION`, `NOT_FOUND`, `CONFLICT`, `INTERNAL`, from the presentation-layer plan) has no slot for the 401s this feature introduces (bad login credentials, invalid/expired/revoked refresh token). `AccessDeniedException` (Spring Security's `@PreAuthorize` failure, FR-06) is mapped to 403 via a dedicated `GlobalExceptionHandler` handler rather than a `DomainException`/`ErrorType` case, since it's a framework exception thrown by AOP around the controller method, not something any use case throws.
9. **Routes**: `/api/v1/auth/{register,login,refresh,logout}` are all four `permitAll` (plan-review finding, CRITICAL, fixed — `logout` must be `permitAll` too: `LogoutUseCase` identifies the session from the refresh token in the request body, not a Bearer access token, so gating it behind `authenticated()` would make it unreachable once the 15-minute access token has expired, defeating the point of an explicit logout; see Phase 3's `SecurityFilterChain` bean and Risks) and `/api/v1/users/{PATCH /{id}/role, GET /me}` (both require authentication; `PATCH .../role` additionally requires `@PreAuthorize("hasRole('ADMIN')")`).

## Dependencies
No new external services beyond Spring Security/OAuth2-resource-server/Nimbus JOSE libraries (all Boot-BOM-managed, no explicit versions) and one lightweight `spring-security-crypto` dependency in `application`. Prerequisite work: `domain`'s `User`/`UserRole`/`UserRepository` (already complete, see `plans/domain-layer/plan.md` Phase 2) and the full `presentation-layer` plan (Event/TicketType REST + `GlobalExceptionHandler` foundation this plan extends). A running Docker daemon is required wherever Phase 1's/Phase 2's/Phase 5's Testcontainers-backed tests execute (same pre-existing constraint as `infrastructure`'s and `presentation-layer`'s own tests). A new environment variable, `JWT_SECRET`, is added to `.env.example`/`docker-compose.yml`/`bootstrap`'s `application.yml`, mirroring the existing `${DB_URL}`-style convention — never hardcoded, never committed with a real value.

## Risks
- HIGH: `SecurityConfig`'s `authorizeHttpRequests` rule is the single point of truth for FR-10 ("Event/TicketType controllers... remain reachable without a token, exactly as today"). A too-narrow `permitAll` pattern (e.g. missing a trailing `/**`, or accidentally method-restricted) silently breaks two pre-existing, unmodified test files the moment Phase 3 lands. Mitigation: explicit regression-check steps in Phases 3, 4, and 5 re-run `EventControllerTest`/`TicketTypeControllerTest` unmodified and require them green before proceeding.
- HIGH: `spring-boot-starter-oauth2-resource-server`/`spring-security-oauth2-jose` resolving cleanly against the pinned Boot 4.1.1/Spring Framework 7 BOM was flagged by the spec itself as a plan-level blocker if it fails. Mitigation: Phase 1 adds the dependencies and confirms a clean compile/resolve as its very first step, before any code depends on the new types — cheapest possible point to discover a version conflict.
- MEDIUM: `RefreshTokenStore` living in `application.auth` rather than `domain.repository` is a one-off deviation from this codebase's otherwise-universal port-in-domain pattern (see Research Summary #4). Documented extensively here and in Phase 2 so it reads as a deliberate, reasoned choice rather than an inconsistency a future contributor "fixes" by moving it.
- MEDIUM: storing refresh tokens hashed (never raw) is enforced by convention (the JPA entity structurally has only a `tokenHash` field, no raw-token field to accidentally populate) plus a unit-test-level assertion (`LoginUseCaseTest`/`RefreshUseCaseTest` assert the stored hash never equals the returned raw value) rather than a runtime guard — a careless future edit adding a new field could still reintroduce raw storage. Mitigation: Phase 1's Success Criteria includes a literal `grep`-based structural check (mirrors the domain-layer plan's "no `@Setter`" mechanical verification), re-run in Phase 5's final verification.
- MEDIUM: JWT secret key management beyond local/dev (`.env`-sourced, matching the existing DB-credentials convention) — key rotation, secret-in-git prevention for real deployments — is a named, out-of-scope gap per the brainstorm report, not silently assumed away. No phase in this plan addresses key rotation.
- LOW: `GetUserUseCase`/`/me` resolves identity purely from the JWT's `sub` claim at authentication time — a user deleted after token issuance but before expiry still authenticates at the filter level, only failing with `UserNotFoundException` (500, since it's an unmapped edge case, not a 401) inside `/me`'s own execution. Accepted: no user-deletion feature exists yet anywhere in this codebase.
- LOW: `RefreshUseCase`/`LoginUseCase` share one result shape (`LoginResult { userId, role, refreshToken }`) since both produce byte-for-byte the same data today — acceptable now, would need splitting if a future requirement adds refresh-specific response fields.
- NOTED (plan-review finding): no phase's test suite covers a malformed `Authorization` header (missing `Bearer ` prefix, garbage token, wrong signing key) against a **protected** endpoint end-to-end — `AccessTokenIssuerTest`/`SecurityConfigTest` (Phase 3) test encode/decode round-trips with well-formed input, and Phase 4's `UserControllerTest` covers "no token" but not "malformed token." Accepted as a gap rather than a blocker: Spring Security's `oauth2ResourceServer(...).jwt(...)` filter rejects malformed/invalid-signature tokens with 401 by framework default, so the risk is in un-tested-ness, not un-handled-ness. If picked up later, add one `UserControllerTest` case per malformed-token shape.
- NOTED (plan-review finding): 401 responses can come from two different places with potentially different `ProblemDetail` shapes — `GlobalExceptionHandler`'s `handleDomainException` (for `InvalidCredentialsException`/`InvalidRefreshTokenException`, thrown by use cases) versus Spring Security's own `oauth2ResourceServer` filter (for a missing/malformed/expired Bearer token, rejected before any controller/use-case runs, using Spring Security's default `AuthenticationEntryPoint` response body, not `GlobalExceptionHandler`). Neither the spec nor any phase pins these two 401 shapes to be identical. Accepted for P1: FR-05's acceptance condition only requires a 401 status code, not a specific body shape; revisit if a client ever needs to distinguish or uniformly parse both cases.
- NOTED (plan-review finding): `ChangeUserRoleUseCase` (Phase 2) has no optimistic-locking/version check — two concurrent `PATCH /{id}/role` calls for the same user (e.g. two admins) both read-modify-write without conflict detection, so the second write silently wins with no error to either caller. Accepted for P1: role changes are a low-frequency admin action, not a hot path like refresh-token rotation, and `User`'s domain entity has no `@Version` field today. Revisit if concurrent role-management by multiple admins becomes a real operational pattern.
- RESOLVED (Phase 2 review gate): `RegisterUserUseCase.execute` still keeps `existsByEmail` as a fast-path, but the correctness boundary is now the database unique constraint plus `UserRepositoryImpl.saveAndFlush` translating `DataIntegrityViolationException` to `DuplicateEmailException`. A real two-thread Postgres integration test proves both registrations can pass the pre-check while exactly one succeeds and the other becomes a domain conflict.

### Decisions made this session
- Added explicit `SecurityConfig` imports to the new `@WebMvcTest` classes because this Spring Boot 4 test slice did not auto-import the application security configuration; this makes the 401/403 and `@PreAuthorize` assertions exercise the real filter chain.
- Kept `ObjectMapper` construction local to the new slice tests to match the existing presentation test convention; the current `@WebMvcTest` setup does not expose an `ObjectMapper` bean for test injection.
- Kept `RegisterRequest` structurally role-free and used `@Size(min = 8)` for the transport-level password floor; role assignment remains owned by `RegisterUserUseCase`.
- Added explicit generic return types to all six auth/user beans in `UseCaseConfig`, preserving the composition-root pattern used by the existing Event/TicketType use cases.
- Used Spring Security 7.1's `NimbusJwtEncoder.withSecretKey(...).algorithm(HS256)` builder after the TDD test exposed that the older `ImmutableSecret` constructor could not select a signing key with the pinned Boot 4.1.1 dependency set.
- Kept Spring Security's framework-provided `FACTOR_BEARER` metadata authority and asserted only the application contract (`ROLE_ADMIN` is present and no other application role is granted); `hasRole` checks remain based on `ROLE_*`.
- Added a test-only JWT secret to `bootstrap/src/test/resources/application.yml` and a local-dev secret to ignored `.env` so full-context tests and Docker Compose do not depend on a real deployment secret.
- Extracted `RefreshTokenIssuer` (package-private, `application.auth`) as the single point owning refresh-token TTL policy and issue-and-wrap-in-`LoginResult` logic, called by both `LoginUseCase` and `RefreshUseCase` — previously duplicated verbatim including a separately-declared `REFRESH_TOKEN_TTL_DAYS` constant in each class.
- Added `AuthApiSmokeTest` with a real random-port HTTP client (`RestTemplate` + JDK request factory) so concurrent refresh/register checks cross the servlet filter chain and database boundary instead of using simulated `MockMvc` concurrency; the client is configured to capture expected 401/409 responses rather than throwing them.
- Kept the existing fixed JWT test secret in `bootstrap/src/test/resources/application.yml`; Phase 5 required no configuration or production-code change beyond the new integration test.
- Re-ran the explicit security gates: no direct raw refresh token persistence call sites, zero Spring/JPA/Jackson imports under `domain/src/main/java`, and the pre-existing Event/TicketType smoke tests remained green in the 390-test reactor run.
- Declined to add a `UserNotFoundException.forId(UUID)` static factory (suggested by the Simplification agent to dedup 3 call sites) — checked against the codebase's existing convention (`EventNotFoundException` is constructed inline with string concatenation at 4 call sites, no factory) and concluded a factory would introduce inconsistency with sibling exceptions rather than remove it.
- Declined to fix `RegisterUserUseCase`'s check-then-act duplicate-email race in the simplify step — genuine finding, but a correctness bug is out of scope for `/simplify` by its own rules ("that is what `/code-review` is for"); documented in Risks instead so Step 4 catches it with full authority to fix.
