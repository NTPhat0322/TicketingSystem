# Phase 5: E2E Integration Tests + Final Verification

## P1 Stories Satisfied
- All 6 P1 stories, proven end-to-end against a real Postgres instance (via Testcontainers) through the full Spring context — the only point in this plan where register → login → protected-call → refresh → logout → role-change are exercised together as one continuous flow, matching how `plans/presentation-layer/phase-04-e2e-smoke-tests-and-verification.md` closed out that feature.

## Requirements
A new `bootstrap/src/test/java/com/tienphat/ticketingsystem/auth/AuthApiSmokeTest.java`, extending the existing `AbstractPostgresIntegrationTest` base (real `@ServiceConnection PostgreSQLContainer`, full `Application` context, `TestRestTemplate` or `MockMvc` over the real servlet stack — matching `EventApiSmokeTest`'s exact style), drives one continuous flow per test method: register a CUSTOMER → login with those credentials → call `GET /api/v1/users/me` with the returned access token (proves FR-05 end-to-end against a real, persisted user) → call `POST /api/v1/auth/refresh` twice in sequence with the same original refresh token (first succeeds and rotates, second must fail — proves single-chain rotation, FR-08, against a real row in a real `refresh_tokens` table) → call `POST /api/v1/auth/logout` with the latest refresh token → confirm a subsequent refresh attempt with that now-logged-out token fails. A second, separate test method seeds a second user and proves the ADMIN role-change path (`PATCH /{id}/role` by an admin-role token succeeds; by a non-admin-role token is rejected) against real persisted rows. This phase also runs the plan's closing verification gates: a literal grep confirming no raw refresh-token value is ever passed to any persistence call (spec's explicit security check), a domain-purity re-check (domain module still has zero framework imports — auth's new exceptions didn't leak anything in), and a full reactor test run with a final tally.

### Tests to Write First
This phase is integration-first rather than strict red→green unit TDD (mirroring `phase-04-e2e-smoke-tests-and-verification.md`'s own framing — these tests exercise already-green units together for the first time, so "write first" here means "write before declaring the feature done," not "before any implementation exists"):
- `AuthApiSmokeTest#fullAuthLifecycle_succeeds`: register → login → `GET /me` (200, matches registered profile) → refresh #1 (200, new token pair, different from the original) → refresh #2 reusing the *original* (now-rotated-away) refresh token (401 `InvalidRefreshTokenException`) → logout with the latest valid refresh token (204) → refresh #3 with that now-revoked token (401).
- `AuthApiSmokeTest#registerRejectsClientSuppliedRole`: register with an extra `"role":"ADMIN"` field in the raw JSON body → 201 with `role == CUSTOMER`, then a direct repository-level check (via the real `UserRepository` bean, injected into the test) confirms the persisted row's role is `CUSTOMER` — the strongest possible proof of FR-01's role-ignoring guarantee, since it inspects the actual database row, not just the response DTO.
- `AuthApiSmokeTest#roleChange_requiresAdmin`: seed two registered users; promote one to ADMIN directly via the repository (test setup, not through the API — there is no bootstrap-an-admin endpoint by design); admin token can `PATCH` the other user's role successfully (200, persisted); the non-admin user's own token attempting the same `PATCH` on itself is rejected (403).
- `AuthApiSmokeTest#concurrentRefresh_onlyOneWins` (plan-review finding, HIGH — HTTP-level closure of `RefreshTokenStoreImplTest`'s Phase 2 DB-level concurrency proof): register → login to obtain one real refresh token → fire two real concurrent `POST /api/v1/auth/refresh` requests presenting that same token (`ExecutorService`/two `CompletableFuture`s calling the real servlet stack, not `MockMvc`'s simulated one) → assert exactly one response is 200 with a fresh token pair and the other is 401 `InvalidRefreshTokenException`. This is the only test in the whole plan that exercises the race through the full stack (controller → use case → `RefreshTokenStoreImpl` → real Postgres), rather than at a single layer in isolation.
- `AuthApiSmokeTest#concurrentRegister_onlyOneWins` (plan-review finding, HIGH — closes a gap the second review round found in Phase 1's duplicate-email fix): fire two real concurrent `POST /api/v1/auth/register` requests with the same email (`ExecutorService`/two `CompletableFuture`s against the real servlet stack) → assert exactly one response is 201 and the other is 409 `DuplicateEmailException`, and a direct repository check confirms exactly one `User` row exists for that email. This is the only test anywhere in the plan that actually proves `UserRepositoryImpl.save`'s `saveAndFlush` + `DataIntegrityViolationException`-translation fix works under real concurrency — Phase 1's own `UserRepositoryImplTest` calls `save` outside any surrounding use-case transaction, so it cannot exercise the deferred-flush failure mode this test targets.
- A non-test **Step**: grep the full `infrastructure` and `application` source trees for any call site passing a raw (un-hashed) token string to a JPA save/query method — confirms `RefreshTokenCrypto.hash(...)` is applied before every persistence boundary crossing, per the spec's explicit security requirement that raw tokens are never stored.
- A non-test **Step**: re-run the domain-purity grep check (`plans/presentation-layer/phase-04...`'s precedent — grep `domain/src/main/java` for any `org.springframework`/`jakarta.persistence`/`com.fasterxml.jackson` import) — confirms the 4 new domain exceptions and `ErrorType.UNAUTHORIZED` introduced zero framework coupling.

## Success Criteria
- `AuthApiSmokeTest` (all 5 methods) passes against a real Testcontainers Postgres instance.
- The refresh-token single-chain rotation is proven against a real persisted row: reusing a rotated-away token fails, a fresh rotation succeeds.
- `concurrentRefresh_onlyOneWins` proves exactly one of two truly concurrent `/auth/refresh` calls on the same token succeeds — the HTTP-level closure of the atomic `revokeIfActive` guard introduced in Phase 2.
- `concurrentRegister_onlyOneWins` proves exactly one of two truly concurrent `/auth/register` calls with the same email succeeds — the HTTP-level closure of Phase 1's `saveAndFlush` + `DataIntegrityViolationException`-translation fix.
- The client-supplied-role-ignored guarantee is proven at the database row level, not just the HTTP response.
- Raw-token-never-persisted grep check returns zero hits outside of `RefreshTokenCrypto`'s own hashing call site.
- Domain-purity grep check returns zero hits.
- `./mvnw test` passes across all 5 modules; final tally recorded in `plan.md` Session Notes.

## Risks
- HIGH: Testcontainers-backed tests are the first point a real Postgres schema is exercised for `users`/`refresh_tokens` — if Hibernate's `ddl-auto: update` (or an equivalent schema-generation step) doesn't produce a working `refresh_tokens` table matching `RefreshTokenJpaEntity`'s mapping, every test in this phase fails at context-startup, not at assertion time. Mitigated by Phase 1's own `RefreshTokenJpaRepositoryTest` (module-level Testcontainers test) already having proven the entity mapping works before this phase runs.
- MEDIUM: this phase is the first time `SecurityConfig`'s `permitAll` rules and `AuthController`/`UserController` are exercised together through the *actual* servlet filter chain (not `MockMvc`'s simulated one) — a subtle mismatch (e.g. a trailing-slash or context-path difference) could pass every `@WebMvcTest` in Phase 4 yet fail here. Mitigated by using the same `TestRestTemplate`/real-port pattern `EventApiSmokeTest` already validated for this exact concern.
- LOW: seeding an ADMIN user for `roleChange_requiresAdmin` bypasses the API (direct repository write in test setup) since no bootstrap-admin endpoint exists by design (spec's Out of Scope) — this is expected test-only scaffolding, not a production gap.
