# Phase 3: TicketType Use-Cases

## P1 Stories Satisfied
- "As an organizer, I want to create a TicketType under an Event so that I can define a price tier and inventory. Accepted when: `CreateTicketTypeUseCase` persists a new `TicketType` (status `ACTIVE`, `soldQuantity = 0`) via `TicketTypeRepository.save()`."
- "As an organizer, I want to update a TicketType's details (name, price, quantities, hold duration) so that I can correct configuration before/while selling. Accepted when: `UpdateTicketTypeUseCase` loads by id, applies changes, and saves — without touching `soldQuantity`, `status`, or `version` directly (those are domain-owned transitions)."
- "As an organizer, I want to view a single TicketType by id. Accepted when: `GetTicketTypeUseCase` returns the mapped `TicketTypeResult` or a not-found error."
- "As an organizer, I want to list all TicketTypes for an Event. Accepted when: `ListTicketTypesByEventUseCase` calls `TicketTypeRepository.findAllByEventId()` and returns mapped results."
- "As an organizer, I want to deactivate a TicketType so that it stops accepting sales. Accepted when: `DeactivateTicketTypeUseCase` calls `TicketType.close()` and saves — surfacing `TicketTypeNotAvailableException` if the transition is invalid."

## Requirements
All 5 TicketType use-cases exist, compile against Phase 1's foundation and Phase 2's worked `EventNotFoundException` pattern, and are independently unit-tested. `TicketType` gains the `updateDetails(...)` mutator this phase needs — `TicketType.java` today has no way to change `name`/`price`/`totalQuantity`/`maxPerUser`/`holdDurationSec` after `create()`, and the stories require one that never touches `soldQuantity`/`version` directly (status is re-derived, per the red-team fix below). `testing: --tdd` — every item below is written as a failing test before the production code that satisfies it.

## Files to Create/Modify
- MODIFY `domain/src/main/java/com/tienphat/domain/model/TicketType.java` — add `updateDetails(String name, Money price, int totalQuantity, int maxPerUser, int holdDurationSec)`:
  - Throws `TicketTypeNotAvailableException` if `status == CLOSED` (mirrors `close()`'s terminal semantics — editing price/capacity on a tier the organizer already stopped selling is meaningless, same rationale as `EventStatus`'s terminal states blocking `Event.updateDetails`).
  - Otherwise reuses the existing `requireNotNull`/`requirePositive` helpers `create()` already has (throwing `InvalidTicketTypeDataException`), and rejects `totalQuantity < soldQuantity` (new but minimal guard — a lower bound the field's own meaning implies, since capacity can't drop below what's already sold).
  - **Never assigns `soldQuantity` or `version`**, but — unlike the original draft of this mutator — **does re-derive `status` after applying the new `totalQuantity`**, using the same `SOLD_OUT ⟺ soldQuantity == totalQuantity` invariant `confirmSale`/`releaseSale` already maintain: if `totalQuantity == soldQuantity`, transition to `SOLD_OUT`; if the tier was `SOLD_OUT` and the new `totalQuantity > soldQuantity`, transition back to `ACTIVE`. (Grounding gap found in red-team review: the first draft only guarded `totalQuantity >= soldQuantity` and left `status` untouched, which let a capacity increase on a `SOLD_OUT` tier silently keep it marked sold out — or a capacity decrease on an `ACTIVE` tier silently skip the `SOLD_OUT` transition — corrupting the invariant `confirmSale`/`releaseSale` rely on.)

## Steps
1. Write `TicketTypeTest#updateDetails_*` (red), then add the `TicketType.updateDetails(...)` mutator to make it pass (green) — must land before `UpdateTicketTypeUseCase`.
2. Create `TicketTypeResult` and the MapStruct `TicketTypeMapper`, including the custom `Money`/`BigDecimal` conversion. No test precedes this — mechanical mapping, exercised indirectly by the use-case tests below.
3. Write `CreateTicketTypeUseCaseTest` (red), then implement `CreateTicketTypeUseCase` + `CreateTicketTypeCommand` (green), wiring in the `EventRepository` pre-check ahead of `TicketType.create(...)`.
4. Write `UpdateTicketTypeUseCaseTest` (red), then implement `UpdateTicketTypeUseCase` + `UpdateTicketTypeCommand` (green), converting the incoming `BigDecimal` price to `Money` via `Money.of(...)` before calling `updateDetails`.
5. Write `GetTicketTypeUseCaseTest` and `ListTicketTypesByEventUseCaseTest` (red), then implement `GetTicketTypeUseCase` and `ListTicketTypesByEventUseCase` (green) — both read-only, no `@Transactional`.
6. Write `DeactivateTicketTypeUseCaseTest` (red), then implement `DeactivateTicketTypeUseCase` + `DeactivateTicketTypeCommand` (green).
7. Run the full `application` + `domain` test suite and confirm `CreateTicketTypeUseCase`'s transaction wraps exactly one `TicketTypeRepository.save()` call (the `EventRepository.findById` pre-check is read-only and does not count as a second aggregate save, per the accepted plan decision).

## Risks
- The new `totalQuantity < soldQuantity` guard in `updateDetails` is an addition beyond what any P1 story text states explicitly: mitigate by keeping it a single `InvalidTicketTypeDataException` check (same exception type `create()` already uses for bad quantities) and pinning it with one dedicated test, so it reads as a deliberate, minimal decision rather than scope creep.
- `CreateTicketTypeUseCase` depending on two repositories is the first use-case in this slice with more than one collaborator: mitigate by keeping the `EventRepository` usage strictly read-only (`findById` only, never `save`) so the "one aggregate save per transaction" success criterion stays true, and asserting that explicitly in the test (`verify(eventRepository, never()).save(any())`).
- `updateDetails` blocking on `status == CLOSED` (added in red-team review) plus re-deriving `SOLD_OUT`/`ACTIVE` from the new `totalQuantity` is new domain behavior beyond the original draft — mitigate by pinning both with dedicated `TicketTypeTest` cases (already listed above) so the status-recomputation logic isn't just implied by the use-case tests.
- `UpdateTicketTypeCommand` requires every field (no partial-update semantics), same as Phase 2's `UpdateEventCommand` — an omitted field silently nulls/zeros it out. Out of scope for this phase per FR-08 (presentation validates required fields before calling the use-case); flagged here, parallel to Phase 2's note, so the presentation-layer request DTO design handles it in both places consistently.
