# Plan: Application Module — Event & TicketType Use Cases (P1)
Status: 🟡 In Progress
Date: 2026-09-19
Mode: Hard
Test: --tdd

## Overview
Stand up the `application` Maven module's first slice: 10 Clean-Architecture use-case classes (Create/Update/Get/List/Deactivate for `Event` and `TicketType`) that orchestrate the already-complete `domain` aggregates and repository ports, so organizers can manage Events and TicketTypes before any Order/Payment flow exists.

## Phases
- [ ] Phase 1: Domain foundation — `PageRequest`/`PageResult`, `EventRepository.findAll`, `EventNotFoundException`/`TicketTypeNotFoundException`, `application/pom.xml` deps, shared `UseCase<I, O>` interface
- [ ] Phase 2: Event use-cases — Create/Update/Get/List/Deactivate, `EventResult`, `EventMapper`, and the new `Event.updateDetails(...)` domain mutator
- [ ] Phase 3: TicketType use-cases — Create/Update/Get/ListByEvent/Deactivate, `TicketTypeResult`, `TicketTypeMapper`, and the new `TicketType.updateDetails(...)` domain mutator

## Dependency-Graph Reasoning for Phase Ordering
- Phase 1 must land first: every later use-case implements the shared `UseCase<I, O>` interface, every write use-case needs `@Transactional` (⇒ `spring-tx` in the pom), every mapper needs MapStruct on the classpath, `ListEventsUseCase` needs `PageRequest`/`PageResult` + `EventRepository.findAll`, and every `Get*`/`Deactivate*`/`Update*` use-case needs the new not-found exceptions. None of Phase 2/3's code compiles without Phase 1.
- Phase 2 before Phase 3: not a hard technical dependency (Phase 3 only needs `EventRepository`/`EventNotFoundException`, both delivered in Phase 1) — this is an aggregate-ownership ordering choice. `TicketType.create` requires an existing `Event`, so modeling Event's own CRUD surface first keeps the plan's reading order matching the domain's dependency direction (`TicketType` → `Event` lookup, never the reverse). Phase 3's `CreateTicketTypeUseCase` reuses the `EventNotFoundException` decision already exercised by Phase 2's `GetEventUseCase`/`UpdateEventUseCase`, so writing Phase 2 first gives Phase 3 a worked example to follow rather than inventing the not-found pattern twice independently.
- Within each aggregate phase: the domain mutator addition (`updateDetails`) is a prerequisite step inside that phase, not pulled into Phase 1, because it is aggregate-specific and only that phase's `Update*UseCase` needs it — keeping Phase 1 scoped to genuinely cross-cutting additions.

## Research Summary
Two prior researcher passes (see `plans/reports/260918-application-layer-brainstorm.md`) converged on: use-case/interactor shape over a mediator or coarse application-service split; reuse of existing domain repository ports rather than redefining them in `application`; `@Transactional` (accepting `spring-tx` as a dependency) over a hand-rolled `UnitOfWork` port; a generic `UseCase<I, O>` interface plus one Command/Result type per use-case; Bean Validation and authorization left entirely to `presentation`; domain exceptions bubbling up uncaught rather than wrapped in a Result/Either; and MapStruct for DTO mapping since the parent `pom.xml` already reserves `mapstruct.version`.

A follow-up planning pass (this plan) locked the concrete shape: aggregate-first packages (`application/event/...`, `application/tickettype/...`) each holding their own use-cases, one `Result` record, and one MapStruct mapper per aggregate; Command/Query types colocated per use-case rather than a shared generic CRUD DTO, with `Get*`/`List*` inputs kept to a bare `UUID` or the domain `PageRequest` directly (no bespoke wrapper record) while `Create*`/`Update*`/`Deactivate*` each get a real `*Command` record; MapStruct mappers constructor-injected (`componentModel = "spring"`), used only for the `Entity → Result` direction — `Command → Entity` calls go through the domain factory/mutator directly, since those require validated construction order the mapper cannot express; `CreateTicketTypeUseCase` doing a read-only `EventRepository.findById` pre-check (not a second save) before calling `TicketType.create`; and adding `EventNotFoundException`/`TicketTypeNotFoundException` to `domain.exception` (extending `DomainException`, same one-message-constructor pattern as every existing exception there) rather than inventing a second, inconsistent not-found exception family.

**Grounding finding surfaced while reading the current domain source (new, not in either prior report):** neither `Event` nor `TicketType` exposes any mutator for its editable fields today — `Event` only has `create`/`reconstitute`/`publish`/`startSale`/`close`/`cancel`, and `TicketType` only has `create`/`reconstitute`/`confirmSale`/`releaseSale`/`close`. The P1 stories for `UpdateEventUseCase`/`UpdateTicketTypeUseCase` require a domain method to actually apply field changes. Decision: add `Event.updateDetails(...)` (Phase 2) and `TicketType.updateDetails(...)` (Phase 3) as new guarded mutators, following the exact validation-helper and exception patterns `create()` already uses — this is a domain addition, not an application-layer workaround, keeping FR-02 ("no business rule re-implemented in the application layer") true.

**Red-team review correction (post-review, applied directly to Phase 3):** the first draft of `TicketType.updateDetails` only guarded `totalQuantity >= soldQuantity` and never touched `status`, which let a `totalQuantity` change silently break the `status == SOLD_OUT ⟺ soldQuantity == totalQuantity` invariant `confirmSale`/`releaseSale` rely on (e.g. raising capacity on a `SOLD_OUT` tier left it stuck `SOLD_OUT`; lowering capacity to match `soldQuantity` on an `ACTIVE` tier never flipped it to `SOLD_OUT`). Fixed by having `updateDetails` re-derive `status` the same way `confirmSale`/`releaseSale` do, and by blocking the call entirely with `TicketTypeNotAvailableException` when `status == CLOSED` (mirroring `Event.updateDetails`'s DRAFT-only restriction, since editing a terminally closed tier has no defined meaning). See phase-03's Files/Steps/Success-Criteria for the exact behavior.

## Dependencies
None external (no new services, no queues, no cache). Prerequisite work: `domain` module (complete, see `plans/domain-layer/plan.md`). Blocked on nothing else. `application/pom.xml` gains `spring-tx` and `mapstruct`/`mapstruct-processor` — both resolved via the parent `spring-boot-starter-parent` BOM / the already-declared `mapstruct.version` and `lombok-mapstruct-binding.version` properties, so no new version pins are introduced.

## Risks
- MEDIUM: `Event`/`TicketType` currently expose no update mutator (grounding finding above) — adding `updateDetails(...)` mid-plan touches a domain module previously marked complete. Mitigation: reuse the exact same private validation helpers and exception types `create()` already throws, so no new invariant surface or exception type is introduced by the addition; each new mutator gets its own domain-level unit tests in the same phase.
- MEDIUM: MapStruct + Lombok annotation-processor chain (`lombok-mapstruct-binding` ordering in `maven-compiler-plugin`) is new to this codebase — misconfiguration silently produces a mapper that ignores Lombok-generated getters instead of failing loudly. Mitigation: Phase 1's success criteria requires `application` to compile with the wiring in place before any mapper is written in Phase 2/3.
- LOW: `PageRequest`/`PageResult` page-indexing convention (0- vs 1-based) is undocumented upstream. Mitigation: pin 0-indexed explicitly in the Phase 1 Javadoc and a dedicated boundary test, before any use-case consumes it.
- LOW: Accepting `spring-tx` breaks the module's previous zero-framework-dependency stance (noted as an accepted trade-off in the prior brainstorm report already). Not re-opened here; flagged only so a future "make application pure POJO again" request is recognized as a full use-case refactor, not a config tweak.
- LOW (Rejected alternative, not reopened): a coarser `EventApplicationService`/`TicketTypeApplicationService` (one class per aggregate, one method per operation) was considered instead of 10 separate use-case classes. Rejected because the spec's FR-01 already locks one-class-per-use-case, and later phases (Order checkout orchestrating `StockCachePort`, Payment confirmation) will need the fine-grained shape anyway — switching to a coarse service now only to split it again later is net-negative churn. The one surviving caveat from that research (boilerplate concern) is already addressed by keeping `Get*`/`List*` Command types minimal.

### Findings from red-team review (`plan-reviewer`, 2026-09-19)
Two HIGH findings were code-verified defects and are already fixed directly in phase-02/phase-03 (not just logged here): (1) every `orElseThrow(XxxNotFoundException::new)` snippet was a guaranteed compile failure since `EventNotFoundException`/`TicketTypeNotFoundException` only have a `(String message)` constructor — replaced with `orElseThrow(() -> new XxxNotFoundException(...))` lambdas throughout; (2) `TicketType.updateDetails`'s original guard didn't preserve the `SOLD_OUT ⟺ soldQuantity == totalQuantity` invariant — fixed by having it re-derive `status` and blocking on `CLOSED` (see the grounding note above and phase-03). The following NOTED findings are logged here as accepted residual risk rather than plan changes:
- MEDIUM: No idempotency handling on `CreateEventUseCase`/`CreateTicketTypeUseCase` — a retried/duplicated create request produces a second, distinct aggregate (new generated id), nothing de-duplicates. Acceptable for this P1 CRUD slice with no user-facing retries wired up yet; the organizer can deactivate the duplicate. Flag for presentation-layer design (idempotency key or client-side guard) in a later phase.
- MEDIUM: Concurrent edits to the same `Event`/`TicketType` are "last write wins" until infrastructure adds optimistic locking — `Update*UseCase` does a plain `findById → mutate → save` with no version re-check. Consistent with the domain's own documented design (`TicketType.version` javadoc: "mirrors the schema's optimistic-lock column... domain code never changes it"), so not a defect in this plan; the infra-layer plan for this module must not silently drop this.
- MEDIUM: Mutating Commands (`UpdateEventCommand`, `DeactivateEventCommand`, `UpdateTicketTypeCommand`, `DeactivateTicketTypeCommand`) carry only the resource id, no caller/organizer identity — deliberate per the spec's Out-of-Scope authorization decision, but it means presentation can't check "does this organizer own this resource" without an extra fetch-and-compare against `EventResult.organizerId`. No structural hook exists for it at the use-case layer. Not a defect in this phase (no endpoints exist yet); carried forward for the next phase's presentation/API design.
