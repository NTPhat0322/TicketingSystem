# Phase 2: Event REST Layer

## P1 Stories Satisfied
- "As an API client, I want to create/update/get/list/deactivate an Event via REST so that I can manage events without touching the database directly. Accepted when: all 5 Event endpoints (`POST`, `PUT`, `GET /{id}`, `GET` list, `POST /{id}/deactivate` or equivalent) return correct status codes and bodies against real Postgres." — the `MockMvc`-level half lands here; the "against real Postgres" half is confirmed in Phase 4.
- Partial: "invalid input... rejected with a 400" and "every domain exception... translated into a consistent RFC 7807 `ProblemDetail`" — this phase adds the Event-specific DTO validation annotations and is the first place `GlobalExceptionHandler` (Phase 1) gets exercised through an actual HTTP request instead of a direct unit test.

## Requirements
All 5 Event endpoints (FR-01 through FR-05) exist on `EventController`, backed by the 5 real Event use-case classes wired as typed `UseCase<I,O>` beans in a new `presentation.config.UseCaseConfig`. Request DTOs carry Jakarta Bean Validation annotations matching `Event`'s actual domain invariants (required fields; deliberately *no* `@Future` — see `plan.md`'s Research Summary for why). All Request↔Command and Result↔Response mapping goes through a MapStruct `EventDtoMapper`. Verified with `@WebMvcTest` slices — no real Spring context, no real database yet.

### Tests to Write First
Write each of these (red) before the class it targets exists, then implement just enough to turn it green:
- `EventDtoMapperTest` (non-mocked, `@SpringBootTest`-free unit test instantiating the MapStruct-generated impl directly or via `Mappers.getMapper`, mirroring `application`'s `EventMapperTest` pattern): `CreateEventRequest → CreateEventCommand` preserves every field; `(UUID id, UpdateEventRequest) → UpdateEventCommand` preserves the path-supplied `id` plus every body field; `EventResult → EventResponse` preserves every field including `status`, `createdAt`, `updatedAt`. Drives `EventDtoMapper` (Step 1).
- `EventControllerTest` (`@WebMvcTest(EventController.class)`, five typed `@MockitoBean UseCase<...>` fields — one per Event use-case; `GlobalExceptionHandler` is auto-detected by `@WebMvcTest`, no `@Import` needed):
  - `POST /api/v1/events` with a fully valid body → 201, response body matches the mocked `EventResult` mapped to `EventResponse`, and the mocked `createEventUseCase` is invoked with a `CreateEventCommand` matching the request. A body missing `name` (or blank `venueName`, or `null organizerId`) → 400 `ProblemDetail`, use-case never invoked.
  - `GET /api/v1/events/{id}` with an id the mocked `getEventUseCase` resolves → 200 with the mapped body. An id the mock rejects with `EventNotFoundException` → 404 `ProblemDetail`. A syntactically invalid path segment (e.g. `"not-a-uuid"`) → 400 `ProblemDetail` (exercises Phase 1's `MethodArgumentTypeMismatchException` handler through real Spring MVC path-variable binding, not just a unit test).
  - `GET /api/v1/events?page=0&size=10` → 200, response envelope's `content`/`page`/`size`/`totalElements`/`totalPages` match the mocked `PageResult<EventResult>`.
  - **[plan-review ACCEPTED]** `GET /api/v1/events?page=-1` → 400 `ProblemDetail`, mocked use-case never invoked. `GET /api/v1/events?size=0` → 400 `ProblemDetail`, mocked use-case never invoked. These exercise `@Validated` + `@Min` on the controller's `@RequestParam`s together with Phase 1's `ConstraintViolationException` handler (added there specifically for this) — without it, both cases would fall through to the generic `Exception → 500` fallback instead of 400, since `org.springframework.data.domain.PageRequest.of(...)` throws a plain `IllegalArgumentException`, not a `DomainException`.
  - `PUT /api/v1/events/{id}` with a valid body → 200, mapped body matches. Unknown id (mock throws `EventNotFoundException`) → 404. Mock throws `InvalidEventScheduleException` (e.g. simulating `startTime` not before `endTime`) → 400.
  - `POST /api/v1/events/{id}/deactivate` → 200 with updated `status` in the response. Unknown id → 404. Mock throws `InvalidEventStateException` (illegal transition, e.g. already `CANCELLED`) → 400.
  Drives `EventController` + the 5 `UseCaseConfig` Event `@Bean` methods (Steps 2–4).

- CREATE `presentation/src/main/java/com/tienphat/presentation/event/EventDtoMapper.java` — `@Mapper(componentModel = "spring")`. `CreateEventCommand toCommand(CreateEventRequest request)`. `UpdateEventCommand toCommand(UUID id, UpdateEventRequest request)` (`@Mapping(target = "id", source = "id")`). `EventResponse toResponse(EventResult result)`. **[plan-review ACCEPTED]** Plus an explicit, hand-written default method (not auto-derived — MapStruct can't infer a field with no source counterpart across two different generic parameterizations): `default PageResponse<EventResponse> toPageResponse(PageResult<EventResult> pageResult) { List<EventResponse> content = pageResult.content().stream().map(this::toResponse).toList(); int totalPages = pageResult.size() == 0 ? 0 : (int) Math.ceilDiv(pageResult.totalElements(), pageResult.size()); return new PageResponse<>(content, pageResult.page(), pageResult.size(), pageResult.totalElements(), totalPages); }` — guards `size == 0` explicitly (division-by-zero) rather than assuming the controller's validation always prevents it from reaching this method.

Each method delegates to its injected `UseCase<I,O>.execute(...)` then maps the result via `EventDtoMapper`; no business logic in the controller itself.

## Success Criteria
- All 5 Event endpoints exist, each returning the status code specified by FR-01..05, verified by `EventControllerTest` against mocked use-cases.
- `EventDtoMapperTest` confirms every field survives `CreateEventRequest → CreateEventCommand`, `(id, UpdateEventRequest) → UpdateEventCommand`, and `EventResult → EventResponse`.
- A missing/blank required field in `CreateEventRequest`/`UpdateEventRequest` produces 400 before the mocked use-case is ever invoked (verified via `Mockito.verifyNoInteractions`/`verify(..., never())`).
- A malformed UUID in `GET /api/v1/events/{id}` produces 400 via `GlobalExceptionHandler`, not a raw Spring error page — confirms Phase 1's `MethodArgumentTypeMismatchException` handler engages correctly through real path-variable binding.
- `./mvnw -pl presentation -am test` passes.

## Risks
- **[plan-review ACCEPTED]** `@Validated`-triggered `ConstraintViolationException` (from `@Min` on `page`/`size`) is a *different* exception type from `MethodArgumentNotValidException` (from `@Valid @RequestBody` failures) — Phase 1's `GlobalExceptionHandler` must add a dedicated handler for it, or the negative-`page`/zero-`size` test cases above fall through to the generic 500 fallback instead of 400. Cross-referenced in `phase-01`'s Files/Steps.
- `EventController`'s `PUT`/deactivate handlers depend on the mocked use-case actually throwing the exception under test (`EventNotFoundException`/`InvalidEventScheduleException`/`InvalidEventStateException`) rather than the controller catching and re-mapping it itself — if a future edit adds a stray `try/catch` in the controller, `GlobalExceptionHandler` would silently stop being exercised for that path. Mitigation: controller methods stay a single `execute(...)` call plus a mapper call, no local exception handling, enforced by code review rather than a test (a test can't easily distinguish "handler ran" from "controller happened to build the same response manually").
- No `@Future` validation on date fields (see `plan.md`) is a deliberate deviation from FR-12's literal example — if a future reviewer re-reads FR-12 in isolation without `plan.md`'s Research Summary, they may flag it as a missed requirement. Mitigation: the deviation and its rationale are documented in both `plan.md` and this phase file, not just implied by omission.
- `PageResponse` is a new shared DTO shape with no precedent elsewhere in the codebase — if its field names don't match what API consumers/tests expect (e.g. `totalPages` vs `totalElements`-only), it's a breaking rename later. Mitigation: named directly after `PageResult`'s own fields (`content`, `page`, `size`, `totalElements`) plus a derived `totalPages`, keeping the envelope a faithful projection of the domain type it wraps.
