# Phase 1: Exception Handling Foundation

## P1 Stories Satisfied
- "As an API client, I want invalid input (missing required fields, negative price/quantity, malformed UUIDs) rejected with a 400 and a structured error body, before it ever reaches a use-case. Accepted when: Jakarta Bean Validation annotations on request DTOs cause `@Valid` failures to short-circuit into a 400 `ProblemDetail`." — this phase builds the `MethodArgumentNotValidException`/`MethodArgumentTypeMismatchException` handling half of that story (the DTO annotations themselves land in Phases 2/3).
- "As an API client, I want every domain exception (not-found, concurrent update, invalid state/data) translated into a consistent RFC 7807 `ProblemDetail` response, not a raw stack trace or generic 500. Accepted when: a single `@RestControllerAdvice` maps each relevant domain exception to the correct HTTP status and `ProblemDetail` body." — this is this phase's primary deliverable, satisfied fully.

## Requirements
`domain` gains a small, framework-free `ErrorType` enum and a `DomainException.errorType()` default method (returns `INTERNAL`), overridden by the 8 exceptions actually reachable through the 10 Event/TicketType use-cases. `presentation` gains a single `GlobalExceptionHandler` (`@RestControllerAdvice`) that maps `ErrorType → HttpStatus → ProblemDetail` for any `DomainException`, handles `@Valid` failures and malformed path-variable UUIDs as 400s, and falls back to a generic, non-leaking 500 for anything else. No controllers exist yet — this phase is verified with direct unit tests against the handler class itself, not `@WebMvcTest`.

### Tests to Write First
Write each of these (red) before the class/method it targets exists, then implement just enough to turn it green:
- `DomainExceptionErrorTypeTest` (`domain`, plain JUnit — no Spring): asserts `errorType()` for each of the 8 relevant exceptions returns the expected `ErrorType` (`EventNotFoundException`/`TicketTypeNotFoundException` → `NOT_FOUND`; `TicketTypeConcurrentUpdateException`/`TicketTypeNotAvailableException` → `CONFLICT`; `InvalidEventDataException`/`InvalidEventScheduleException`/`InvalidEventStateException`/`InvalidTicketTypeDataException` → `VALIDATION`), plus one case instantiating a minimal anonymous `DomainException` subclass that does *not* override `errorType()` and asserting it defaults to `INTERNAL`. Drives the `ErrorType` enum and every subclass edit.
- `GlobalExceptionHandlerTest` (`presentation`, plain unit test — instantiates `GlobalExceptionHandler` directly, no Spring context needed):
  - Each of the 8 mapped exceptions, passed directly to the `DomainException` handler method, produces a `ProblemDetail` with the exact expected `HttpStatus` (404/404/409/409/400/400/400/400) and a `detail` equal to the exception's message.
  - An unmapped `DomainException` subclass (e.g. a throwaway test double, or reusing `InvalidMoneyException`) produces a 500 `ProblemDetail` via the same handler method (confirms the default-`INTERNAL` path, not just the 8 overridden cases).
  - A constructed/mocked `MethodArgumentNotValidException` with two field errors produces a 400 `ProblemDetail` whose body includes both field names/messages (structure, not raw exception text).
  - A constructed/mocked `MethodArgumentTypeMismatchException` (simulating a malformed UUID path variable) produces a 400 `ProblemDetail`.
  - A generic `Exception` (e.g. `RuntimeException`) produces a 500 `ProblemDetail` whose body contains no stack trace and no raw exception message (a fixed, generic detail string instead) — pins the "no unmapped exception reaches the client as a raw 500 with a stack trace" success criterion at its narrowest, most direct point.
  - **[plan-review ACCEPTED]** A constructed `ConstraintViolationException` (simulating a `@Validated` `@RequestParam` failure, e.g. Phase 2's `page`/`size` bounds) produces a 400 `ProblemDetail`. Needed because it's a distinct exception type from `MethodArgumentNotValidException` (that one only covers `@Valid @RequestBody`/path-variable validation, not simple `@RequestParam`/`@PathVariable` constraints under class-level `@Validated`) — without this handler, Phase 2's negative `page`/`size` test cases fall through to the generic 500 fallback instead of 400.

## Steps
1. Add `ErrorType` to `domain` and write `DomainExceptionErrorTypeTest` (red for the 8 override cases; the default-`INTERNAL` case can pass immediately once `errorType()` exists on the base class).
2. Add the `errorType()` default method to `DomainException`, then override it on the 8 relevant subclasses to turn the remaining red cases green.
3. Add `spring-boot-starter-test` to `presentation/pom.xml`.
4. Write `GlobalExceptionHandlerTest` end to end (red) — including the `MethodArgumentNotValidException`/`MethodArgumentTypeMismatchException` cases, which need a way to construct or mock those exception types without a running Spring context.
5. Implement `GlobalExceptionHandler`'s five `@ExceptionHandler` methods (`DomainException`, `MethodArgumentNotValidException`, `MethodArgumentTypeMismatchException`, `ConstraintViolationException`, `Exception`) to turn the test green, one method at a time.
6. Run `./mvnw -pl domain,presentation -am test` and confirm all new tests pass alongside the existing suite.
7. `grep` `domain/src/main/java/com/tienphat/domain/exception/` for `org.springframework`/`jakarta.persistence`/`jakarta.validation` imports — confirm zero matches (`ErrorType`/`DomainException` stay framework-free).

## Success Criteria
- `ErrorType` has exactly 4 values; `DomainException.errorType()` defaults to `INTERNAL`; the 8 listed subclasses each return their specified `ErrorType`, pinned by `DomainExceptionErrorTypeTest`.
- `GlobalExceptionHandlerTest` confirms all 8 mapped exceptions produce the correct `HttpStatus`, the unmapped-exception default path produces 500, `@Valid`-style failures, malformed-UUID-style failures, and `ConstraintViolationException` (`@Validated` param failures) all produce 400, and a generic `Exception` produces a 500 with no leaked message/stack trace.
- `grep -rn "org.springframework\|jakarta.persistence\|jakarta.validation" domain/src/main/java/com/tienphat/domain/exception/` returns zero matches.
- `./mvnw -pl domain,presentation -am test` passes.

## Risks
- Choosing a **default** (not abstract) `errorType()` method means the 16 `DomainException` subclasses outside this spec's scope (Order/Payment/Ticket/User) silently inherit `INTERNAL` without anyone having decided that's correct for them — acceptable today (nothing exposes them over HTTP yet) but worth flagging so a future presentation-layer spec for those aggregates doesn't assume the mapping was already reviewed.
- `MethodArgumentTypeMismatchException` is easy to forget entirely — it's not a `DomainException` subtype, so a naive implementation that only handles `DomainException` + `MethodArgumentNotValidException` would leave malformed-UUID path variables falling through to Spring's default (non-`ProblemDetail`) error response, silently failing the "malformed UUIDs... rejected with 400" acceptance criterion. Mitigation: it has its own explicit test case in this phase, before any controller exists to exercise it end-to-end (that end-to-end confirmation happens in Phase 2).
- Constructing a real `MethodArgumentNotValidException`/`MethodArgumentTypeMismatchException` outside a running Spring MVC request context can be awkward (both expect a `MethodParameter` and, for the former, a `BindingResult`) — if the test resorts to a loose Mockito stub that doesn't reflect the real exception's actual getter behavior, it could pass without proving the handler works against the real thing. Mitigation: Phase 2's `EventControllerTest` re-exercises the same two handlers through an actual `@WebMvcTest` request, which is the stronger of the two signals if they disagree.
