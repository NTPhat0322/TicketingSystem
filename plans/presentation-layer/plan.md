# Plan: Presentation Layer — REST API for Event & TicketType
Status: 🟢 Complete
Date: 2026-09-21
Mode: Hard
Test: --tdd

## Overview
Expose the 10 already-complete Event/TicketType use-cases over HTTP: 10 REST endpoints across `EventController`/`TicketTypeController`, Jakarta Bean Validation on request DTOs, MapStruct DTO↔Command/Result mapping, manual `@Bean` wiring of the plain-class use-cases, and a single `@RestControllerAdvice` translating every domain exception into an RFC 7807 `ProblemDetail` — so an external client can manage events and ticket types without touching the database or any use-case class directly.

## Phases
- [x] Phase 1: Exception handling foundation — `ErrorType` enum in `domain`, `DomainException.errorType()`, 8 relevant subclass overrides, `GlobalExceptionHandler` in `presentation`
- [x] Phase 2: Event REST layer — DTOs, `EventDtoMapper`, `UseCaseConfig` (Event beans), `EventController` — 5 endpoints (FR-01..05)
- [x] Phase 3: TicketType REST layer — DTOs, `TicketTypeDtoMapper`, `UseCaseConfig` (TicketType beans), `TicketTypeController` — 5 endpoints (FR-06..10)
- [x] Phase 4: End-to-end smoke tests + final verification — full-context Testcontainers smoke tests in `bootstrap`, domain-purity re-check, full reactor test run

## Dependency-Graph Reasoning for Phase Ordering
- Phase 1 must land first: every controller test in Phases 2/3 asserts a specific HTTP status + `ProblemDetail` shape for `EventNotFoundException`, `MethodArgumentNotValidException`, malformed-UUID path variables, etc. Without `ErrorType`/`DomainException.errorType()`/`GlobalExceptionHandler` in place first, those assertions have nothing to run red against — they'd either not compile (no `ErrorType` symbol) or pass vacuously (no handler, so Spring's default error page shape, not `ProblemDetail`).
- Phase 2 before Phase 3: no hard technical dependency (`TicketTypeController` only needs `TicketType`'s own use-cases/DTOs), but `CreateTicketTypeUseCase` validates `eventId` against `EventRepository.findById` — Phase 3's controller test for the cross-aggregate 404 (FR-06) reads more naturally once `EventController`/`EventDtoMapper` conventions are already established in Phase 2 to mirror. `UseCaseConfig` also grows incrementally: Phase 2 adds the 5 Event `@Bean` methods, Phase 3 adds the 5 TicketType ones to the same file, rather than one 10-bean file appearing atomically.
- Phase 4 last: `presentation`'s own `pom.xml` only depends on `application` (by design — a hexagonal adapter never depends on another adapter), so a real end-to-end smoke test against a live Postgres needs both `infrastructure` (the real `EventRepositoryImpl`/`TicketTypeRepositoryImpl` beans) and `presentation` (the controllers) on the same classpath. Only `bootstrap` depends on both. Phase 4 therefore adds Testcontainers test infrastructure to `bootstrap`, not `presentation`, and is the only phase that can prove the full wire-up (bean config → controller → use-case → real DB) actually works.

## Research Summary
This plan is grounded in decisions already settled during a prior brainstorm/context-gathering pass (not re-litigated here):
1. **Use-cases stay plain classes.** All 10 are constructed manually via `@Bean` methods in a new `presentation.config.UseCaseConfig`, injecting the already-Spring-managed `EventRepository`/`TicketTypeRepository` (from `infrastructure`, wired at `bootstrap` composition-root time) and `EventMapper`/`TicketTypeMapper` (from `application`). Each `@Bean` method's *declared* generic return type (`UseCase<CreateEventCommand, EventResult>`, not a raw/erased type) is what makes Spring's generic-aware autowiring resolve the correct bean into each controller field — this is the crux of the whole design and is called out explicitly as a risk below.
2. **DTO↔Command/Result mapping uses MapStruct**, `@Mapper(componentModel = "spring")` style — mirroring `application`'s `EventMapper`/`TicketTypeMapper`, not infrastructure's static `Mappers.getMapper(...)` (test-only there). No `@ObjectFactory` needed: presentation DTOs are flat records, not domain aggregates with private constructors.
3. **Exception handling: domain-owned `ErrorType`, single generic advice.** `ErrorType` (`VALIDATION`, `NOT_FOUND`, `CONFLICT`, `INTERNAL`) lives in `domain` (no `HttpStatus`/Spring leakage). `DomainException` exposes it via a **default method** returning `INTERNAL`, overridden only by the 8 exceptions actually reachable through the 10 Event/TicketType use-cases — not all 24 `DomainException` subclasses, which would mean touching Order/Payment/Ticket/User exception classes unrelated to this spec's scope for no behavioral benefit (nothing exposes them over HTTP yet). `GlobalExceptionHandler` maps `ErrorType → HttpStatus → ProblemDetail` in one `@ExceptionHandler(DomainException.class)`, plus dedicated handlers for `MethodArgumentNotValidException` (`@Valid` failures) and `MethodArgumentTypeMismatchException` (malformed UUID path variables — not a `DomainException` at all, easy to miss), plus a generic `Exception` fallback so nothing reaches the client as a raw 500 with a stack trace.
4. **Testing: mixed.** `@WebMvcTest` slices with typed `@MockitoBean UseCase<I,O>` fields (a legitimate seam since every use-case implements the shared interface) for fast controller-level tests; a small number of full `@SpringBootTest` + Testcontainers + MockMvc smoke tests (one per aggregate) in `bootstrap`, mirroring `infrastructure`'s `AbstractPostgresIntegrationTest` pattern, to prove the real wiring. `@MockBean` is deprecated as of Spring Boot 3.4+ in favor of `org.springframework.test.context.bean.override.mockito.MockitoBean` (Spring Framework 6.2+) — this project is on `spring-boot-starter-parent:4.1.1`, so all new tests use `@MockitoBean`, never `@MockBean`.
5. **Routes**: `/api/v1/events` (`POST`, `GET /{id}`, `GET` paginated list, `PUT /{id}`, `POST /{id}/deactivate`) and `/api/v1/ticket-types` (`POST`, `GET /{id}`, `PUT /{id}`, `POST /{id}/deactivate`) plus `/api/v1/events/{eventId}/ticket-types` (`GET`, non-paginated list) — all 10 FRs map 1:1 to an endpoint.
6. **No auth/security** — explicitly out of scope, confirmed twice during brainstorm.
7. `presentation/config/OpenApiConfig.java` stays untouched; every new file lands alongside it.

A grounding pass (this plan) resolved three details the spec left open:
- **`TicketTypeNotAvailableException` → `CONFLICT` (409), not `VALIDATION` (400).** It fires when closing/updating an already-`CLOSED` ticket type — a state conflict against the current resource, not malformed input in the request itself.
- **No `@Future` on request DTO date fields**, despite FR-12's example. `Event`'s domain invariant only enforces `startTime.isBefore(endTime)` / `saleStartTime.isBefore(saleEndTime)` — it never requires dates to be in the future. Adding `@Future` would be *stricter* than the domain invariant it's supposed to mirror (FR-12's own framing: "matching domain invariants already enforced downstream") and would break legitimate historical/test data. Ordering violations are still caught, just by the domain (`InvalidEventScheduleException` → 400 via `GlobalExceptionHandler`), not by Bean Validation.
- **`InvalidMoneyException` (thrown by `Money.of()` on a negative amount) is deliberately left unmapped**, falling through to `DomainException`'s default `INTERNAL` (500) if ever reached. It is not reachable through this API surface: `CreateTicketTypeRequest`/`UpdateTicketTypeRequest.price` carry `@PositiveOrZero`, so a negative price is rejected as a 400 `MethodArgumentNotValidException` before any use-case (and therefore `Money.of()`) ever runs. Flagged as a risk below rather than silently left undocumented.

## Risks
- **[plan-review NOTED]** `Event` has no optimistic locking (`TicketType` does — `version` field + `TicketTypeConcurrentUpdateException`). Two concurrent `PUT /api/v1/events/{id}` calls silently last-write-wins with no 409, asymmetric with the TicketType flow. Pre-existing infra-layer behavior, out of this plan's file scope — flagged for a future spec, not fixed here.
- **[plan-review NOTED]** No idempotency-key handling on `POST /api/v1/events`/`POST /api/v1/ticket-types` — a client retry after a timeout can silently create a duplicate resource (`CreateEventUseCase`/`CreateTicketTypeUseCase` always mint a fresh `UUID.randomUUID()`). Not addressed by this plan; worth a decision (accept, or add an `Idempotency-Key` header contract) in a future iteration.
- **[plan-review NOTED]** All mutating endpoints are unauthenticated by explicit design (see spec.md Out of Scope) — confirmed by review to still hold across every phase file (no partial/sneaked-in auth). Real risk if ever deployed publicly as-is; the spec's "must not deploy to public/prod" guardrail is the only current mitigation.
- HIGH: `UseCaseConfig`'s `@Bean` methods rely on Spring resolving autowire candidates by *declared* generic return type (`UseCase<CreateEventCommand, EventResult>`), since `UseCase<I,O>` is otherwise type-erased at runtime — if any `@Bean` method's return type is widened (e.g. declared as `Object` or a raw `UseCase`) or two methods accidentally share an identical generic signature, Spring either fails to inject (`NoSuchBeanDefinitionException`) or injects ambiguously. Mitigation: Phase 2/3's `@WebMvcTest` controller tests fail immediately and loudly (context load failure) if a `@MockitoBean UseCase<X,Y>` field doesn't find a real counterpart bean shape — this is exercised well before the Phase 4 full-context smoke test.
- MEDIUM: `TicketTypeNotAvailableException` mapping to 409 vs 400 is a judgment call the spec explicitly left open ("planner should pick one"). Mitigation: documented above with rationale (state conflict, not malformed input); pinned by an explicit test case in Phase 3.
- MEDIUM: `presentation` has no compile-time dependency on `infrastructure` by design (hexagonal boundary), so nothing in Phases 1–3 can prove the real `EventRepositoryImpl`/`TicketTypeRepositoryImpl` beans actually satisfy `UseCaseConfig`'s wiring — a bean-name or generic-signature mismatch would only surface at `bootstrap` runtime. Mitigation: Phase 4 exists specifically to close this gap before considering the feature done.
- LOW: `InvalidMoneyException` (and other `DomainException` subclasses outside this spec's 8) fall through to the default `INTERNAL` (500) `ErrorType` — correct/safe (never a raw stack trace) but not specifically tested per-exception. Mitigation: Phase 1's `GlobalExceptionHandler` test includes one case using a bare, unmapped `DomainException` subclass to confirm the default path itself (500, structured `ProblemDetail`, no leak), rather than assuming it from the 8 mapped cases alone.
- LOW: `@MockitoBean` (replacing `@MockBean`) is a relatively recent API (Spring Framework 6.2+); if the resolved `spring-boot-starter-parent:4.1.1` BOM pulls a different package location or the deprecated `@MockBean` is actually still required, Phase 2's first controller test surfaces this immediately as a compile error, before it propagates into Phase 3.
- LOW: Adding `errorType()` to `DomainException` as a **default** method (not abstract) is a deliberate scope-limiting choice — it means 16 of 24 `DomainException` subclasses (Order/Payment/Ticket/User, none exposed over HTTP yet) silently inherit `INTERNAL` rather than being forced to declare an explicit type. Acceptable now; revisit (or make abstract) once those aggregates get their own controllers in a future spec.

- **Found and fixed a real production bug** (not a test artifact): `bootstrap.Application` lives in package `com.tienphat.ticketingsystem`, which is not an ancestor package of `com.tienphat.infrastructure`. Spring Data JPA's auto-configured repository/entity scanning derives its base package from the `@SpringBootApplication` class's own package (via `AutoConfigurationPackages`), not from `scanBasePackages` (that only governs component scanning).
