# Phase 3: TicketType REST Layer

## P1 Stories Satisfied
- "As an API client, I want to create/update/get/list/deactivate a TicketType via REST so that I can manage ticket tiers under an event. Accepted when: all 5 TicketType endpoints work end-to-end, including the `eventId` existence check surfacing as 404 when the event doesn't exist." — the `MockMvc`-level half lands here; the "end-to-end" half is confirmed in Phase 4.
- Continues: "invalid input... rejected with a 400" (TicketType-specific validation: blank name, negative/zero price, non-positive quantity) and "every domain exception... translated into `ProblemDetail`" (adds `TicketTypeConcurrentUpdateException` → 409 and `TicketTypeNotAvailableException` → 409 as newly-exercised, TicketType-only paths).

## Requirements
All 5 TicketType endpoints (FR-06 through FR-10) exist on `TicketTypeController`, including the event-scoped list (`GET /api/v1/events/{eventId}/ticket-types`, FR-09). Backed by the 5 real TicketType use-case classes wired as typed `UseCase<I,O>` beans, added to the same `presentation.config.UseCaseConfig` Phase 2 started. Request DTOs carry Jakarta Bean Validation annotations matching `TicketType`'s domain invariants (`@Positive` quantities/limits, `@PositiveOrZero` price — `TicketType`/`Money` explicitly allow a free, zero-price tier). All Request↔Command/Result↔Response mapping goes through a MapStruct `TicketTypeDtoMapper`. Verified with `@WebMvcTest` slices, same as Phase 2.

## Risks
- `@PositiveOrZero` on `price` is a deliberate choice (free tiers are a real domain case, per `TicketType`'s own Javadoc) — if a reviewer expects `@Positive` by default without checking `Money`'s zero-allowed invariant, it reads like a validation gap rather than an intentional match to the domain rule. Mitigation: called out explicitly in this phase's Requirements, not left implicit in the DTO annotation alone.
- `InvalidMoneyException` (thrown only if a negative amount somehow reaches `Money.of()`) is never exercised by this phase's tests, since `@PositiveOrZero` rejects negative prices before any use-case runs — this is an intentional gap already flagged in `plan.md`'s Risks, repeated here so it isn't mistaken for an oversight specific to this phase.
- `GET /api/v1/events/{eventId}/ticket-types` returns a bare JSON array (`List<TicketTypeResponse>`), not a `PageResponse`-style envelope, since FR-09 doesn't ask for pagination — if a later spec adds pagination here, it's a breaking response-shape change for existing clients, not additive. Mitigation: intentional per FR-09's literal wording; noted here so the tradeoff is visible before any future change.
