## Risks
- **[plan-review ACCEPTED]** `bootstrap/src/main/java/com/tienphat/ticketingsystem/Application.java` declares `class Application` — package-private, no `public` modifier. Both smoke test classes sit in subpackages (`com.tienphat.ticketingsystem.event`, `.tickettype`), so `@SpringBootTest(classes = Application.class, ...)` would fail to compile ("Application is not public... cannot be accessed from outside package"). Fixed above by dropping the explicit `classes =` argument and relying on `@SpringBootTest`'s default upward package search instead — no change to `Application.java`'s visibility needed.
- Testcontainers needs a running Docker daemon wherever `./mvnw -pl bootstrap -am test` (or the full reactor `./mvnw test`) executes — if CI lacks Docker, this phase's tests fail with an infrastructure error unrelated to any code defect, exactly as flagged for `infrastructure`'s own Testcontainers setup. Mitigation: same known constraint, not new to this phase; `infrastructure`'s tests already require it, so CI either already has it or the whole suite was already failing before this phase.
- `bootstrap/src/test/resources/application.yml` shadowing (not merging with) `bootstrap/src/main/resources/application.yml` depends on Maven's default test-classpath-before-main-classpath ordering — if that assumption is ever wrong for this project's build setup, the unresolved `${DB_URL}` placeholder would surface as a confusing property-binding failure with no obvious connection to this phase's change. Mitigation: this is the exact pattern `infrastructure/src/test/resources/application.yml` already uses successfully in the prior plan; Step 3's `EventApiSmokeTest` run is the first, immediate confirmation it still holds here.
- Two smoke tests (one per aggregate) is a deliberately small surface — most branch coverage (validation failures, every exception mapping, pagination edge cases) already lives in Phases 1–3's fast `@WebMvcTest`/unit tests. If a future regression is specific to real-Postgres behavior (e.g. an actual optimistic-lock conflict under `TicketTypeConcurrentUpdateException`) rather than wiring, these two tests may not catch it. Mitigation: that exact scenario is already covered by `infrastructure`'s own `TicketTypeRepositoryImplTest` concurrency test from the prior plan — this phase's smoke tests are intentionally scoped to wiring, not re-proving persistence-layer correctness already proven elsewhere.
