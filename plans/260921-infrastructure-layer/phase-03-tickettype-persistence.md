# Phase 3: TicketType Persistence

## P1 Stories Satisfied
- "As the application layer, I want `TicketTypeRepository.save()`/`findById()`/`findAllByEventId()` backed by a real Postgres-persisted `TicketType`, so that all 5 TicketType use-cases work end-to-end. Accepted when: a `TicketTypeRepository` Spring bean exists in `infrastructure`, backed by `TicketTypeJpaEntity` + Spring Data JPA."
- "As a maintainer, I want domain aggregates to stay JPA-free..." (TicketType portion — `TicketType.java` receives no new annotations; its existing plain `int version` field is untouched.)
- "As a maintainer, I want a concurrent `TicketType` update (stale `version`) to surface as a domain exception, so that `application`/`presentation` never need to know about Hibernate's exception types. Accepted when: `TicketTypeJpaEntity` has `@Version int version`; the repository adapter catches `ObjectOptimisticLockingFailureException` on save and rethrows a new `TicketTypeConcurrentUpdateException` (domain-owned)."
- "As a maintainer, I want repository adapters verified against a real Postgres instance..." (TicketType portion, plus the optimistic-lock conflict path specifically.)

## Requirements
`TicketTypeJpaEntity` (with `@Version int version`), `TicketTypePersistenceMapper` (Money↔BigDecimal conversion, `reconstitute(...)`-based `@ObjectFactory`, `version` carried in both mapping directions), `TicketTypeJpaRepository` (with a derived `findAllByEventId`), and `TicketTypeRepositoryImpl` exist in `infrastructure`, together implementing the `TicketTypeRepository` port exactly. A new domain exception `TicketTypeConcurrentUpdateException` is added to `domain.exception`; `TicketTypeRepositoryImpl.save()` catches `ObjectOptimisticLockingFailureException` specifically (not the broader `DataAccessException`) and rethrows it as this new exception. `TicketType.java` itself is untouched. `testing: --tdd` — every item below is written as a failing test before the production code that satisfies it, run against the real Postgres container from Phase 1.

### Tests to Write First
Write each of these (red) before the class it targets exists, then implement just enough to turn it green:
- `TicketTypePersistenceMapperTest` (non-mocked, `Mappers.getMapper(...)`-based, same pattern as `application`'s `TicketTypeMapperTest` and Phase 2's `EventPersistenceMapperTest`): round-trips a fully-populated `TicketType` through `toEntity` then `toDomain`, asserting every field is preserved exactly — explicitly including `price` (`Money ↔ BigDecimal`) and `version`, the two fields most likely to be silently dropped. Drives `TicketTypeJpaEntity` + `TicketTypePersistenceMapper` (Step 2).
- `TicketTypeRepositoryImplTest` (class name ends in `Test`, not `IT` — no `maven-failsafe-plugin` in this project, so `mvn test`'s default Surefire include glob (`**/*Test.java`) is what actually runs; an `*IT.java` name would be silently skipped, leaving the build green while the Postgres-backed tests never execute) — extends `AbstractPostgresIntegrationTest` from Phase 1:
  - `save` then `findById` returns a `TicketType` matching the one saved on every field, including `price` and `version` — asserted via AssertJ `usingRecursiveComparison()` or explicit per-field assertions, **not** `.isEqualTo()`/domain `.equals()` (`TicketType` uses `@EqualsAndHashCode(of = "id")`, so a bare `.isEqualTo()` would pass even if `price` or `version` were silently dropped in the round trip).
  - `findById` on an unknown id returns `Optional.empty()`.
  - `findAllByEventId` returns every `TicketType` for a given event and an empty list for an event with none.
  Drives `TicketTypeJpaRepository` + `TicketTypeRepositoryImpl`'s `save`/`findById`/`findAllByEventId` (Step 3).
- `TicketTypeRepositoryImplTest#save_staleVersion_throwsConcurrentUpdateException`: save a `TicketType`, load it into two independent in-memory copies (simulating two concurrent editors), save the first copy (its `version` advances in the database), then attempt to save the second, now-stale copy — asserting a `TicketTypeConcurrentUpdateException` is thrown, and explicitly asserting it is never a raw `ObjectOptimisticLockingFailureException` escaping the adapter. Drives the `try`/`catch` translation in `TicketTypeRepositoryImpl.save()` (Step 4) and the new `TicketTypeConcurrentUpdateException` type itself.
- `TicketTypeUseCaseIntegrationTest` (extends `AbstractPostgresIntegrationTest`, wires the real `CreateTicketTypeUseCase`/`UpdateTicketTypeUseCase`/`GetTicketTypeUseCase`/`ListTicketTypesByEventUseCase`/`DeactivateTicketTypeUseCase` — no mocks — backed by the real `TicketTypeRepositoryImpl` and Phase 2's real `EventRepositoryImpl`): happy path through each of the 5 use-cases against the live database, completing the spec's "10 total" use-case acceptance criterion together with Phase 2's `EventUseCaseIntegrationTest`. Drives the final Spring wiring (Step 5).

## Files to Create/Modify
- CREATE `domain/src/main/java/com/tienphat/domain/exception/TicketTypeConcurrentUpdateException.java` — extends `DomainException`, the same single-message constructor every existing exception in that package uses (matching `EventNotFoundException`/`TicketTypeNotFoundException`'s precedent from the `application`-layer plan). No dedicated unit test — it is a pure structural addition exercised by `TicketTypeRepositoryImplIT`'s concurrency test instead.
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/tickettype/TicketTypeJpaEntity.java` — `@Entity`, `@Table(name = "ticket_types")`, assigned (not generated) `UUID` `@Id`; fields mirror `TicketType` 1:1 (`eventId`, `name`, `price` as a `BigDecimal` column, `totalQuantity`, `soldQuantity`, `maxPerUser`, `holdDurationSec`, `status` as an enum column, `createdAt`, `updatedAt`), plus `@Version int version` mapped to the domain's existing `version` field.
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/tickettype/TicketTypePersistenceMapper.java` — `@Mapper(componentModel = "spring")`. `TicketTypeJpaEntity toEntity(TicketType ticketType)` via plain getters plus a hand-written `default BigDecimal map(Money price)` (same style as `application`'s `TicketTypeMapper`). `TicketType toDomain(TicketTypeJpaEntity entity)` via an `@ObjectFactory` default method calling `TicketType.reconstitute(...)` — `TicketType`'s only constructor is `private`, same reasoning as Phase 2's `Event` mapper — plus a hand-written `default Money map(BigDecimal price)` (`Money.of(...)`) for the reverse direction. `version` is passed straight through in both mapping directions — no exclusion, no default value.
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/tickettype/TicketTypeJpaRepository.java` — `interface TicketTypeJpaRepository extends JpaRepository<TicketTypeJpaEntity, UUID>` with a derived `List<TicketTypeJpaEntity> findAllByEventId(UUID eventId)`; infra-internal, never imported outside `infrastructure`.
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/tickettype/TicketTypeRepositoryImpl.java` — `@Repository implements TicketTypeRepository`. `findById`/`findAllByEventId` delegate to `TicketTypeJpaRepository` + `TicketTypePersistenceMapper`. `save(TicketType ticketType)` wraps the `TicketTypeJpaRepository.save(...)` call in a `try`/`catch (ObjectOptimisticLockingFailureException e)` that rethrows `new TicketTypeConcurrentUpdateException(...)` — no other exception type is caught here.
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/tickettype/TicketTypePersistenceMapperTest.java`
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/tickettype/TicketTypeRepositoryImplTest.java`
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/tickettype/TicketTypeUseCaseIntegrationTest.java`

## Steps
1. Add `TicketTypeConcurrentUpdateException` to `domain.exception` — a pure structural addition, no test precedes it (mirrors the `EventNotFoundException`/`TicketTypeNotFoundException` precedent).
2. Write `TicketTypePersistenceMapperTest` (red) — explicitly asserting `price` and `version` survive the round trip — then create `TicketTypeJpaEntity` and `TicketTypePersistenceMapper` (including the `@ObjectFactory` method routing to `TicketType.reconstitute(...)` and both `Money`/`BigDecimal` conversion methods) to turn it green.
3. Write `TicketTypeRepositoryImplTest`'s `save`/`findById`/`findAllByEventId` happy-path and empty-result cases (red, recursive/per-field comparison not `.equals()`), then create `TicketTypeJpaRepository` and `TicketTypeRepositoryImpl`'s corresponding methods (green).
4. Write `TicketTypeRepositoryImplTest`'s stale-version concurrency test (red — at this point `save()` either lets the raw Hibernate exception propagate or doesn't conflict-check at all), then add the `try`/`catch (ObjectOptimisticLockingFailureException)` → `TicketTypeConcurrentUpdateException` translation to `TicketTypeRepositoryImpl.save()` (green).
5. Write `TicketTypeUseCaseIntegrationTest` wiring the 5 real TicketType use-cases against the real `TicketTypeRepositoryImpl` + Phase 2's `EventRepositoryImpl` + Postgres (red until wiring resolves), then confirm it turns green with no changes to the use-case classes themselves.
6. Run the full `infrastructure` test suite and confirm `TicketType.java` still has zero `javax.persistence`/`jakarta.persistence` imports and its existing plain `int version` field is unchanged — only `TicketTypeJpaEntity` carries `@Version`.
7. Run `./mvnw -pl infrastructure -am test` for the whole module (Phases 1-3 combined) and confirm the spec's final success criteria: all 10 application-layer use-cases (5 Event + 5 TicketType) pass against real repositories, the optimistic-lock path surfaces the domain exception, zero Flyway/Liquibase dependency was added anywhere, and zero new annotations exist on `domain.model.Event`/`domain.model.TicketType`.

## Success Criteria
- `TicketTypeRepository` is fully backed by a Spring `@Repository` bean (`TicketTypeRepositoryImpl`); `save`/`findById`/`findAllByEventId` all round-trip correctly against the real Postgres container, including `price` and `version`.
- `TicketTypePersistenceMapperTest` passes, confirming `price` (`Money ↔ BigDecimal`) and `version` both survive a full `domain → entity → domain` round trip via `reconstitute(...)`.
- `TicketTypeRepositoryImplTest`'s concurrency test confirms a stale-version concurrent save throws `TicketTypeConcurrentUpdateException` and never a raw `ObjectOptimisticLockingFailureException`.
- `TicketTypeUseCaseIntegrationTest` confirms all 5 application-layer TicketType use-cases run correctly end-to-end against the real repository.
- `grep -rn "javax.persistence\|jakarta.persistence\|org.springframework" domain/src/main/java/com/tienphat/domain/model/TicketType.java` returns zero matches, and `TicketType.java`'s `version` field remains a plain `int` with no annotation.
- Combined with Phase 2: `./mvnw -pl infrastructure -am test` passes, satisfying the spec's "10 total" use-case success criterion, with zero Flyway/Liquibase dependency added anywhere in the project.

## Risks
- Catching the broader `DataAccessException` instead of `ObjectOptimisticLockingFailureException` specifically would silently mislabel unrelated persistence failures (constraint violations, connection drops) as concurrency conflicts. Mitigation: `TicketTypeRepositoryImpl.save()`'s `catch` clause names `ObjectOptimisticLockingFailureException` exactly, pinned by the concurrency test asserting the specific exception type, not just "some exception was thrown."
- Dropping `version` in either `TicketTypePersistenceMapper` direction breaks optimistic locking with no compile error and no obvious runtime error — every save just silently succeeds as if it were a fresh row. Mitigation: both `TicketTypePersistenceMapperTest` (explicit `version` field assertion) and the concurrency test (which would incorrectly pass a "second save silently succeeds" scenario if `version` weren't wired) are written specifically to make this omission fail loudly rather than pass unnoticed.
- `TicketType`'s only constructor is `private` (behind `@Builder(access = PRIVATE)`), same risk class as Phase 2's `Event` — a missing/misnamed `@ObjectFactory` method can produce a mapper that compiles but constructs the wrong object, or fails to compile with an error naming an unrelated symbol. Mitigation: same as Phase 2 — the mapper test's field-by-field assertions catch this before any repository test is written against it.
- `TicketTypeUseCaseIntegrationTest` depends on both `TicketTypeRepositoryImpl` and Phase 2's `EventRepositoryImpl` resolving as beans from the shared test Boot config (`CreateTicketTypeUseCase` needs both). Mitigation: Phase 2 already validated this component-scanning path for `EventRepositoryImpl` alone; this test extends that same validated wiring rather than inventing a new scanning configuration.
