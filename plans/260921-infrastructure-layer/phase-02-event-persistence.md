# Phase 2: Event Persistence

## P1 Stories Satisfied
- "As the application layer, I want `EventRepository.save()`/`findById()`/`findAll(PageRequest)` backed by a real Postgres-persisted `Event`, so that `CreateEventUseCase`, `UpdateEventUseCase`, `GetEventUseCase`, `ListEventsUseCase`, and `DeactivateEventUseCase` work end-to-end. Accepted when: an `EventRepository` Spring bean exists in `infrastructure`, backed by `EventJpaEntity` + Spring Data JPA, and every existing application-layer Event use-case test still passes unmodified against it in an integration test."
- "As a maintainer, I want domain aggregates to stay JPA-free, so that `domain` keeps compiling as a plain POJO module with no framework dependency." (Event portion — `Event.java` receives no new annotations.)
- "As a maintainer, I want repository adapters verified against a real Postgres instance..." (Event portion — save/findById/findAll happy paths.)

## Requirements
`EventJpaEntity`, `EventPersistenceMapper`, `EventJpaRepository`, and `EventRepositoryImpl` exist in `infrastructure`, together implementing the `EventRepository` port exactly (`save`/`findById`/`findAll(PageRequest) → PageResult<Event>`) with pagination resolved at the query level, not in memory. `Event.java` itself is untouched — no new annotations, no `version` field (the spec is explicit: no optimistic locking on `Event` in this phase). `testing: --tdd` — every item below is written as a failing integration/mapper test before the production code that satisfies it, run against the real Postgres container from Phase 1.

### Tests to Write First
Write each of these (red) before the class it targets exists, then implement just enough to turn it green:
- `EventPersistenceMapperTest` (non-mocked, `Mappers.getMapper(...)`-based, same pattern as `application`'s `EventMapperTest`): round-trips a fully-populated `Event` through `toEntity` then `toDomain`, asserting every field (`id`, `organizerId`, `name`, `description`, `venueName`, `startTime`, `endTime`, `saleStartTime`, `saleEndTime`, `status`, `createdAt`, `updatedAt`) is preserved exactly. Drives `EventJpaEntity` + `EventPersistenceMapper` (Step 1).
- `EventRepositoryImplTest` (class name ends in `Test`, not `IT` — the project has no `maven-failsafe-plugin`, so default Surefire include globs (`**/*Test.java`) are what `mvn test` actually runs; an `*IT.java` name would be silently skipped and the test would never execute despite the build reporting green) — extends `AbstractPostgresIntegrationTest` from Phase 1:
  - `save` then `findById` returns an `Event` matching the one saved on every field — asserted via AssertJ `usingRecursiveComparison()` or explicit per-field assertions, **not** `.isEqualTo()`/domain `.equals()` (`Event` uses `@EqualsAndHashCode(of = "id")`, so a bare `.isEqualTo()` would pass even if a non-id field silently got dropped in the round trip).
  - `findById` on an unknown id returns `Optional.empty()`.
  - `findAll(PageRequest)` seeded with more rows than one page, each row's `createdAt` distinct and known: page 0 and page 1 return disjoint content in the expected `createdAt` order, and `totalElements` matches the full seeded count. Postgres gives no ordering guarantee for `LIMIT`/`OFFSET` without an explicit `ORDER BY` — asserting order against a known key (not just "disjoint") is what makes this test actually fail a missing/wrong sort, rather than passing by accident on an untouched, single-transaction dataset.
  Drives `EventJpaRepository` + `EventRepositoryImpl` (Steps 2-3).
- `EventUseCaseIntegrationTest` (extends `AbstractPostgresIntegrationTest`, wires the real `CreateEventUseCase`/`UpdateEventUseCase`/`GetEventUseCase`/`ListEventsUseCase`/`DeactivateEventUseCase` — no mocks — backed by the real `EventRepositoryImpl`): happy path through each of the 5 use-cases against the live database, confirming the spec's acceptance criterion that "every existing application-layer Event use-case test still passes unmodified against it." Drives the final Spring wiring (Step 4).

## Files to Create/Modify
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/event/EventJpaEntity.java` — `@Entity`, `@Table(name = "events")`, assigned (not generated) `UUID` `@Id`; fields mirror `Event` 1:1 (`organizerId`, `name`, `description`, `venueName`, `startTime`, `endTime`, `saleStartTime`, `saleEndTime`, `status` as an enum column, `createdAt`, `updatedAt`). No `@Version` — `Event` has no optimistic locking in this phase.
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/event/EventPersistenceMapper.java` — `@Mapper(componentModel = "spring")`. `EventJpaEntity toEntity(Event event)` via plain getters. `Event toDomain(EventJpaEntity entity)` via an `@ObjectFactory` default method that calls `Event.reconstitute(...)` — MapStruct prefers this factory over any constructor once declared, which matters here since `Event`'s only constructor is `private`.
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/event/EventJpaRepository.java` — `interface EventJpaRepository extends JpaRepository<EventJpaEntity, UUID>`, infra-internal (package-private visibility where practical; never imported outside `infrastructure`).
- CREATE `infrastructure/src/main/java/com/tienphat/infrastructure/event/EventRepositoryImpl.java` — `@Repository implements EventRepository`. `save`/`findById` delegate to `EventJpaRepository` + `EventPersistenceMapper`. `findAll(PageRequest pageRequest)` converts the domain `PageRequest` to `org.springframework.data.domain.PageRequest.of(page, size, Sort.by("createdAt").ascending().and(Sort.by("id").ascending()))` — the `id` tie-breaker keeps ordering deterministic when `createdAt` collides — calls `EventJpaRepository.findAll(Pageable)`, and converts the returned `Page<EventJpaEntity>` to a domain `PageResult<Event>` (`content` mapped item-by-item, `page`, `size`, `totalElements` from `Page`) — a single content query at the query level (`LIMIT`/`OFFSET`), never `findAll()` + in-memory sublist. Note: `Page<T>` itself issues a second `COUNT(*)` query to populate `totalElements` — that is expected and required by the `PageResult` contract, not a defect.
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/event/EventPersistenceMapperTest.java`
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/event/EventRepositoryImplTest.java`
- CREATE `infrastructure/src/test/java/com/tienphat/infrastructure/event/EventUseCaseIntegrationTest.java`

## Steps
1. Write `EventPersistenceMapperTest` (red), then create `EventJpaEntity` and `EventPersistenceMapper` — including the `@ObjectFactory` method routing to `Event.reconstitute(...)` — to turn it green.
2. Write `EventRepositoryImplTest`'s `save`/`findById` happy-path and not-found cases (red, recursive/per-field comparison not `.equals()`), then create `EventJpaRepository` and `EventRepositoryImpl`'s `save`/`findById` methods (green).
3. Write `EventRepositoryImplTest`'s `findAll(PageRequest)` pagination case (red) — seed rows spanning two pages with distinct, known `createdAt` values, assert content order — then implement `EventRepositoryImpl.findAll(...)` as a single `Pageable`-driven query with the explicit `createdAt`+`id` sort (green).
4. Write `EventUseCaseIntegrationTest` wiring the 5 real Event use-cases against the real `EventRepositoryImpl` + Postgres (red until the beans resolve — `EventRepositoryImpl`/`EventPersistenceMapper` need to be picked up by component scanning from the test Boot config in Phase 1), then confirm it turns green with no changes to the use-case classes themselves.
5. Run the full `infrastructure` test suite and confirm `EventRepositoryImpl.findAll`'s content fetch is a single `LIMIT`/`OFFSET` query (never `findAll()` + in-memory sublist) — e.g. by inspecting Hibernate's SQL log during the pagination test. `Page<T>`'s accompanying `COUNT(*)` query is expected and not a violation of this criterion.
6. `grep` `domain/src/main/java/com/tienphat/domain/model/Event.java` and confirm it still has zero `javax.persistence`/`jakarta.persistence`/`org.springframework` imports and no new fields — `domain` stays framework-free.

## Success Criteria
- `EventRepository` is fully backed by a Spring `@Repository` bean (`EventRepositoryImpl`); `save`/`findById`/`findAll` all round-trip correctly against the real Postgres container.
- `EventPersistenceMapperTest` passes, confirming every `Event` field survives a full `domain → entity → domain` round trip via `reconstitute(...)`.
- `EventRepositoryImplTest`'s pagination test confirms `findAll(PageRequest)` returns correctly *ordered* (by `createdAt`, `id` tie-breaker), distinct per-page content and an accurate `totalElements` — pinned against a real multi-row dataset with known ordering, not a single-row happy path or an unordered "disjoint content" check.
- `EventUseCaseIntegrationTest` confirms all 5 application-layer Event use-cases run correctly end-to-end against the real repository, unmodified from their Phase-2-of-`application` unit-test behavior.
- `grep -rn "javax.persistence\|jakarta.persistence\|org.springframework" domain/src/main/java/com/tienphat/domain/model/Event.java` returns zero matches.
- `./mvnw -pl infrastructure -am test` passes.

## Risks
- `Event`'s only constructor is `private` (behind `@Builder(access = PRIVATE)`) — if `EventPersistenceMapper`'s `@ObjectFactory` method is missing or misnamed, MapStruct either fails to compile (no accessible constructor found) or silently resolves to some other visible factory, producing a mapper that compiles but constructs the wrong object. Mitigation: `EventPersistenceMapperTest` asserts every field individually after a round trip, written and run red before the mapper exists, so a wrong-factory bug fails loudly rather than passing on an incomplete assertion.
- A `findAll(PageRequest)` implementation that fetches all rows and slices in memory would still pass a single-page test. Mitigation: the pagination test explicitly seeds more than one page's worth of rows and asserts both `totalElements` and that different pages return different, correctly-ordered content — a naive in-memory-slice bug does not accidentally satisfy this shape as easily as a single-page test would.
- `EventUseCaseIntegrationTest` depends on Spring component scanning picking up `EventRepositoryImpl`/`EventPersistenceMapper` as beans from the Phase 1 test Boot config — if that config's base package is scoped too narrowly, the test fails with a `NoSuchBeanDefinitionException` unrelated to any Event-specific defect. Mitigation: confirmed directly by this test itself in Step 4, before any TicketType wiring (Phase 3) risks repeating the same gap.
