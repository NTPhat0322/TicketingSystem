## Dependency-Graph Reasoning for Phase Ordering
- Phase 1 must land first: Phases 2 and 3 are TDD — every repository test in them needs a real Postgres to fail red against before any adapter code exists. Without Testcontainers wired, a base test config, and a singleton-container base class, there is nothing to write a failing integration test against; the module also has no `@SpringBootConfiguration` of its own today (that lives in `bootstrap`), so `@DataJpaTest`-style tests can't even boot without a test-scope-only config class added first.
- Phase 2 before Phase 3: not a hard technical dependency (`TicketTypeRepositoryImpl` only needs `TicketType`'s own mapper/entity/repository), but `TicketType.eventId` references an `Event`, and the combined use-case integration tests for TicketType creation exercise `EventRepository.findById` as a pre-check (the exact pattern already established in `application`'s `CreateTicketTypeUseCase`) — landing Event persistence first gives Phase 3's integration tests a real `EventRepositoryImpl` to depend on instead of a stub.
- Optimistic locking is scoped entirely to Phase 3: the spec is explicit that `Event` gets no `version` field in this phase (that would be a domain change, not an infra one), so nothing in Phase 2 touches `@Version`/`ObjectOptimisticLockingFailureException` at all.

## Research Summary
A single brainstorm pass (`plans/reports/260921-infrastructure-layer-brainstorm.md`) converged on: separate `EventJpaEntity`/`TicketTypeJpaEntity` classes plus bidirectional MapStruct mappers over annotating the domain aggregates directly (keeps `domain` a plain POJO module); Testcontainers Postgres over H2 for repository tests (the repo already runs `postgres:16-alpine` via `docker-compose.yml`, so tests match runtime); and a new domain-owned `TicketTypeConcurrentUpdateException` translated from Hibernate's `ObjectOptimisticLockingFailureException` inside the adapter, rather than letting a Spring ORM exception type cross the port boundary. Redis stock cache, Outbox persistence, and the presentation layer were all explicitly deferred — this plan stays scoped to exactly the two ports `application` already depends on.

A follow-up grounding pass (this plan) locked four implementation details not yet settled by the brainstorm:
1. **MapStruct entity→domain must use `@ObjectFactory`.** Both `Event`/`TicketType` expose only a private constructor behind `@Builder(access = PRIVATE)` plus the public `create`/`reconstitute` factories — MapStruct cannot call a private constructor, and without an explicit `@ObjectFactory` default method routing to `reconstitute(...)`, it would either fail to compile or (worse) silently pick some other visible method. Domain→entity mapping stays plain getters, no factory needed on that side.
2. **`TicketType.version` must be carried through both mapper directions.** It is not optional plumbing — if `toEntity`/`toDomain` drop it, every save looks like a fresh row to Hibernate's `@Version` check and the optimistic lock silently never fires. Phase 3's mapper test and its concurrency-conflict test both exist specifically to catch this class of regression.
3. **`ObjectOptimisticLockingFailureException` is caught narrowly, inside `save()` only.** Catching the broader `DataAccessException` would also swallow unrelated persistence failures (constraint violations, connection errors) and mislabel them as concurrency conflicts — the catch clause targets exactly the one exception type.
4. **Testcontainers uses `@ServiceConnection` with a manually-managed static container, not `@Testcontainers`/`@Container`.** The two lifecycle styles conflict if mixed on the same field; Phase 1 picks `@ServiceConnection` (Spring Boot 3.1+ convention, and this project is on Spring Boot 4.1.1) with a container started once and shared across the module's tests (singleton pattern), and a test-scope-only minimal Boot config class under `infrastructure/src/test/java` (never `bootstrap`) so `@DataJpaTest`-style tests have a `@SpringBootConfiguration` to find.

## Red-Team Review
`plan-reviewer` ran against spec.md + all phase files. Verdict: **WARN** (0 CRITICAL/security). Three ACCEPTED findings were fixed directly in the phase files before cook:
1. Integration test classes were named `*ImplIT.java` (Failsafe convention), but this project has no `maven-failsafe-plugin` — default Surefire only picks up `**/*Test.java`, so those tests would have been silently skipped by `mvn test` while the build reported green. Fixed: renamed to `EventRepositoryImplTest`/`TicketTypeRepositoryImplTest` throughout Phase 2/3.
2. `EventRepositoryImpl.findAll(PageRequest)` had no explicit sort — Postgres gives no ordering guarantee for `LIMIT`/`OFFSET` without one, so a missing/wrong sort could pass an "assert disjoint content" test by accident. Fixed: Phase 2 now specifies `Sort.by("createdAt").ascending().and(Sort.by("id"))` and its pagination test asserts order against known `createdAt` values, not just disjointness.
3. Phase 2's "exactly one SQL query" success criterion contradicted how `Page<T>` actually works (it always issues a separate `COUNT(*)` alongside the content query). Fixed: reworded to "single `LIMIT`/`OFFSET` content query, `COUNT` from `Page<T>` expected."

Two NOTED findings, carried into Risks below rather than changing plan structure:
- IT-level "field-for-field equal" assertions were ambiguous against `Event`/`TicketType`'s `@EqualsAndHashCode(of = "id")` — a bare `.isEqualTo()` would pass even if non-id fields were dropped. Fixed inline in Phase 2/3 test descriptions (explicit per-field assertions or `usingRecursiveComparison()`, never bare `.isEqualTo()`).
- `EventJpaEntity` (assigned UUID, no `@Version`) always routes through Hibernate's `merge()` path (an extra `SELECT` per save) since Spring Data's `isNew()` heuristic can't tell a fresh entity from an existing one without a version field or `Persistable<UUID>`. No action required unless save-path latency becomes a measured concern — see Risks.

## Risks
- HIGH: `Event`/`TicketType` both hide their constructors behind a private, `@Builder`-generated constructor — if a mapper's `@ObjectFactory` wiring is even slightly wrong (wrong method targeted, missing `@Mapping` for a field `reconstitute` needs), MapStruct can fail in ways that are easy to misdiagnose (compile error naming an unrelated symbol, or a mapper that silently returns nulls). Mitigation: each persistence mapper gets its own non-mocked round-trip test (Phase 2/3, mirroring `application`'s `EventMapperTest`/`TicketTypeMapperTest` pattern) asserting every field survives `domain → entity → domain`, written and run red before the mapper exists.
- HIGH: Dropping `TicketType.version` in either mapper direction breaks optimistic locking silently — no exception, no test failure anywhere except the one test built specifically to catch it. Mitigation: Phase 3's mapper test asserts `version` explicitly, and its dedicated optimistic-lock-conflict integration test would pass incorrectly (second stale save silently succeeds instead of throwing) if `version` isn't wired — making the omission visible rather than latent.
- MEDIUM: Testcontainers needs Docker available in every environment `mvn test` runs — if CI doesn't have Docker, the whole module's tests fail with an infrastructure error unrelated to the code. Mitigation: Phase 1's success criteria pins the container/base-class wiring as its own gate, verified before any repository test is written against it, so a Docker-availability problem surfaces immediately rather than mid-Phase-2/3.
- LOW: `EventRepositoryImpl.findAll(PageRequest)` converting to Spring's `Pageable` must stay a single query-level operation (`LIMIT`/`OFFSET`), never `findAll()` + in-memory sublist, per the spec's explicit non-functional requirement. Mitigation: Phase 2's pagination test seeds more rows than one page and asserts each page's content differs and `totalElements` matches the full count, which a naive in-memory-slice bug would still pass — additionally pinned by keeping `findAll` a one-line delegation to `JpaRepository.findAll(Pageable)`, never a broader fetch.
- LOW: This plan's own test-config class (Phase 1) is a `@SpringBootApplication`/`@Configuration` living under `infrastructure/src/test/java` — a future refactor could accidentally move or copy it into `bootstrap` and create a second, conflicting Boot entry point. Mitigation: Phase 1's success criteria includes a `grep` check confirming the class exists only under `infrastructure/src/test/java`.
- NOTED (red-team review): `Event` has no `version` field, so two concurrent `UpdateEventUseCase` calls are last-write-wins with no conflict signal — unlike `TicketType`. This is an explicit, already-documented spec decision (adding `version` to `Event` would be a domain change, not an infra one), not a gap introduced by this plan; flagged here only so it's consciously carried forward.
- NOTED (red-team review): `EventJpaEntity` uses an assigned (non-generated) `UUID` `@Id` with no `@Version`, so Spring Data's `isNew()` heuristic always treats it as "existing," routing every `save()` — including the first insert — through `merge()` (an extra `SELECT` before insert/update). Functionally correct, no data-loss risk, just an extra round trip. No action required now; if save-path latency becomes a measured concern later, `EventJpaEntity` can implement `Persistable<UUID>` to force `persist()` on first save.
- NOTED (Phase 1 execution): Testcontainers resolves to `2.0.5` via the Spring Boot `4.1.1` BOM, which renamed the JUnit/Postgres modules to `org.testcontainers:testcontainers-junit-jupiter` and `org.testcontainers:testcontainers-postgresql` (the plan's original `junit-jupiter`/`postgresql` artifact ids are the pre-2.x names). `infrastructure/pom.xml` uses the renamed artifacts; Phase 2/3 dependency mentions should assume the same.
